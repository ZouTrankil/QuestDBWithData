### A2：提供统一任务查询接口

**具体做什么：** 让页面能查询任务定义、调度状态、运行历史、阶段进度、产物和失败原因。

**解决什么问题：** 当前多套状态来源分散，任务已注册、进程成功退出、数据真正核验完成容易混淆。

**怎么做：** 为 data 同步账本、Batch、主策略及保留的 Python 任务提供只读适配；响应保留 `runtime`、原 job ID、原 run ID、业务日期和执行时刻。定义状态对应关系，保留原始状态和数据核验状态；支持分页、时间范围、错误分类、心跳及日志尾部脱敏。读取页面不创建运行记录或触发补跑。

**验收：** 同一日期的父子任务可以关联；无记录、等待、跳过、未决、失败、过期和完整完成能区分；某个服务离线不伪装成“没有任务”；历史数据可分页读取。

**依赖：** A1。

### A3：实现任务总览和运行详情页

**具体做什么：** 展示“今天应跑什么、正在跑什么、跑完什么、卡在哪里”，可点开某次运行看依赖和结果。

**解决什么问题：** 用户只能查日志，无法一眼判断当天数据处理进度。

**怎么做：** 在审核确定的前端入口复用现有任务页，增加市场/类别筛选、业务日期选择、调度和数据就绪的独立状态、阶段依赖图、运行耗时、处理量、最后推进时间及受保护的产物链接。保留原始运行身份，避免跨系统 ID 冲突。

**验收：** 从失败总览能定位到具体来源、日期和原因；刷新页面不触发任务；旧日成功记录不会覆盖今日失败，调度器停机或数据过期有明确提示。

**依赖：** A2。首版先完成查看能力。

### A4：按批准清单逐批接管数据任务

**具体做什么：** 将 A1 确认的数据生产职责接到 Java 正式执行链，旧调度退出同一写入职责。

**解决什么问题：** 任务在多个项目分散运行，重复写入和漏更新都难以追踪。

**怎么做：** 每批包含一个完整产品或一组紧密依赖的来源：复用现有 owner/端口，固定输入范围，验证正式目标、修订和恢复，接任务查询；切换时停止旧 writer 的触发，记录切换点和回退条件。Batch `source_*` 仍为隔离链路，不能通过去掉表名前缀冒充正式接管。

**验收：** 对批准范围完成正常、增量、修订、重跑和中断恢复；只有一个正式 writer；新任务出现在任务页，旧历史继续可查。每批单独报告，失败停在该批。

**依赖：** A1 的迁移批次获批，且 A2 已能观测运行。具体来源范围沿用[接管清单](../../docs/formal-sync-takeover.md)。

### A5：增加有状态约束的操作按钮

**具体做什么：** 在任务页提供允许的执行、暂停/恢复调度、取消请求和恢复入口。

**解决什么问题：** 查到问题后还需要手拼 CLI，容易错日期、错范围或重复发起运行。

**怎么做：** 由后端返回可执行动作和阻断原因，沿用原鉴权、幂等、锁和恢复协议；执行前展示明确的日期、证券范围和目标。父阶段管理的子任务不允许绕过依赖单独启动，未决写入先核验原运行。

**验收：** 重复点击不会生成重复写入；暂停调度不会被误解为已中止正在运行的任务；非法恢复、并发 owner 和绕过依赖被拒绝。

**依赖：** A3、对应任务的 A4。不要为尚未接管的任务先开放执行按钮。

## B. 模型、schema 与数据页面

### B1：明确前端可直接消费的 schema 契约

**具体做什么：** 输出模型分类、字段类型、含义、单位、格式、业务键、时间语义、来源链接及可读状态，并给出完整响应例子。

**解决什么问题：** Java 类型、来源格式和数据库类型混在一起；前端无法知道如何渲染，也无法区分模型存在和物理表存在。

**怎么做：** 复用数据目录、dataset 定义及字段资料，补齐 `objectName ↔ datasetId`、分类及样本接口的明确对应。约定 null、日期标记、UTC 时间点、数字精度的 JSON 表达。离线模型和实库字段分别标记来源，差异直接展示。

**注释怎么提供：** 复用[现有字段资料](../../docs/collected-field-documentation.md)，中文含义、来源单位和格式从 `sourceDocumentation` 读取，本地时间语义和转换规则单列；不在前端再维护一份字典。每个字段配示例值及解释，缺失说明显示“待核实”，不猜单位。JSON 保持可解析，注释放在字段说明区，不往可复制的 JSON 中插入注释。

**验收：** 至少提供日线、财务、ETF 三种响应示例；明确真实快照与演示值。日期、单位、待核实字段及不可读取原因都能在接口中识别；不会把全部模型都标记为可读取。

### B2：完善有界真实数据预览

**具体做什么：** 用户选模型后能看少量真实行，按证券和日期查看，并直接复制请求示例。

**解决什么问题：** 只有 schema 仍不知道数据长什么样；空表和查询失败也容易混淆。

**怎么做：** 优先复用现有 sample/受限读取服务，逐个补齐允许预览的读取绑定；限制行数、字段、日期范围和超时，动态对象用登记白名单。返回取样时间、实际数据日期、分页信息和来源。需要时间范围的读取器不强行发无界查询。

**示例怎么切换：** 提供“真实数据 / 演示数据”明确切换，演示模式持续显示“合成示例，非真实行情”。真实查询失败时保留错误，不自动换成演示值。示例随契约维护，覆盖正常值、null 和日期边界；示例不入库，不作为来源验收证据。

**验收：** 日线、财务、ETF 样本可与实库核对；空结果、表不存在、未接读取器、权限不足和服务故障分别反馈；没有任意 SQL 输入或全表扫描入口。

**依赖：** B1。

### B3：完成模型浏览页

**具体做什么：** 左侧按市场/类别选模型，右侧查看字段、真实样本、状态与 API 例子。

**解决什么问题：** 用户需要同时翻源码、CSV 和 API 文档才能看懂一个数据条目。

**怎么做：** 页面复用 B1/B2 接口，提供字段搜索、样本表格/JSON 切换和复制请求；示例明确标记，待核实来源保留提示。对象名、dataset ID、正式/隔离目标和样本日期可见。

**UI 交互怎么安排：**

- 左侧按市场、类别浏览，搜索同时匹配中文名和对象名；选中模型后保留搜索条件和列表位置。右侧顶部常驻模型说明、对象类型、可读状态和数据模式。
- 右侧分“字段说明 / 数据预览 / API 示例”三个页签。字段说明直接列出字段名、中文含义、类型、单位、示例值；长说明点击展开，悬停、键盘聚焦也能查看，不只依赖鼠标提示。
- 数据表头显示“成交量（手）”和 `vol`；点击表头的说明按钮打开对应字段解释。字段搜索同步定位预览列；宽表固定证券、日期列并支持横向滚动，窄屏用字段详情面板查看完整说明。
- 证券、日期和行数放在预览区顶部；只展示读取器支持的筛选项，日期缺失或范围超限就原地提示。点击“查询”再请求，默认 20 行；切换模型清除不适用条件，旧请求结果不能覆盖新模型。
- 加载时显示进度并防止重复提交；无结果展示当前筛选条件和清除入口。未接读取器、无权限、表不存在和服务故障各有原因提示；可重试故障提供“重试”，无真实数据仍可主动切到演示模式。
- 表格与 JSON 切换保留当前结果和筛选；显示实际数据日期、取样时间及是否还有下一页，不把取样时间当作数据新鲜度。API 示例按已执行查询生成，复制后提示成功，凭据使用占位符。

**验收：** 用户能从类别定位 `daily`，点开 `vol` 看单位和演示值，理解 `trade_date` 的语义，再切到真实样本并复制可用请求。用正常、空结果、null、无权限、超时和未接读取器样例检查界面；验证键盘操作、窄屏、快速切换模型及复制反馈。没有样本时仍能看 schema 和明确原因，演示值不会被误认为生产数据。

**依赖：** B1、B2；前端入口与 A3 共用。

## C. L2 无数据事故复盘与修复

### C1：只读取证，复原当天的数据链路

**具体做什么：** 到运行服务器核对 2026-10-19（上海时间）的部署和记录，定位从行情接收到页面显示在哪一步断开。

**解决什么问题：** “快速拉升时没数据”只有表现，不能直接归因于流量过大或数据库。

**怎么做：** 先确认服务器访问入口、进程版本、服务配置、目标证券和异常时间窗口。收集订阅/SUBACK/断线、接收与提交计数、解析拒绝、处理积压、落盘耗时、磁盘与 JVM 状态；核对 SQLite 接收索引、Parquet 提交及时间范围，再查实际 API 请求、读取路径、缓存和页面报错。所有时间统一对齐 UTC 与上海交易时段，日志和证据脱敏留存。

**验收：** 交付按时间排列的证据、受影响证券/区间、数据停在何处及可恢复范围。结论区分“已证明、已排除、证据不足”；缺日志或未接收到的报文不猜造。不先重启、清表或重放，以免改变现场。

**待补信息：** 服务器具体访问方式、发生异常的证券与大致时间、对应页面或请求。执行时优先从已有部署记录和日志确认；找不到再向用户补问。本审核阶段尚未登录服务器。

### C2：按根因修复读写连接与状态反馈

**具体做什么：** 让页面读到已提交的实时结果，并能区分未订阅、待首条、处理积压、数据过期和读取失败。

**解决什么问题：** 采集端可能有数据而消费端读错位置，或者错误被吞掉后统一显示“无数据参考”。

**怎么做：** 以 C1 实际部署为准，逐段修复。若确认 Java Parquet 输出与 Python QuestDB 读取脱节，就提供明确的只读实时结果契约并改消费端；不恢复为第二套 QuestDB 结果 writer。若是解析、积压、资源上限或时间过滤，则针对证据修复对应环节。保留原始落盘和恢复保证；历史回放必须标记为历史，不能伪装实时结果。

**验收：** 事故证券在正确交易日可读取最新已提交结果；故障注入能显示具体原因和最后更新时间；历史数据不能充当当前分钟；重启不重复累计。

**依赖：** C1 根因明确。修复超出既有协议时先提交具体变更方案。

### C3：验证突发流量与恢复，补上可观测指标

**具体做什么：** 用事故保留样本或明确标注的合成数据复现突发流量，验证修复并暴露积压和延迟。

**解决什么问题：** 平稳短测通过，仍无法证明行情突发时结果能及时到达页面。

**怎么做：** 由现场实测确定峰值和验收阈值，复用现有负载工具；验证峰值输入、长时间运行、断线重连和强杀恢复。记录接收→提交→可读→页面显示的各段延迟、积压、拒绝量和空间增长。告警先暴露到状态接口/任务页，通知渠道另定。

**验收：** 达到事先确定的吞吐和延迟目标；恢复后已提交报文不丢失、不重复累计；无法补回的供应商断线区间明确保留缺口。报告区分合成回放、事故原件和真实全天实采。

**依赖：** C2；指标也供 A2/A3 展示。

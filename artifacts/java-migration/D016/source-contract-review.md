# D016 `etf_share` source contract review

Review date: 2026-09-30. Python and the local formal table were read only. Bounded Tushare field and market-scope diagnostics ran on 2026-09-28 and 2026-09-17; no D016 data write was made by those diagnostics.

## Python call path and writer behavior

Primary connector: `D:/work/fund_2/back-monitor/src/quant_platform/data/adapters/connectors/etf/etf_share_sync.py`.

- `_get_etf_share_by_date(trade_date)` calls `pro.fund_share(trade_date=trade_date)` once. The connector decorator is `api_limit=200, period=60`; there is no offset/limit loop or market partition in Python. Network errors and exhausted retries raise `RuntimeError`; they are not represented as an empty-success response.
- `sync_etf_share` obtains its upper bound from `resolve_completed_sync_end_date`, uses `timestamp` as the last-update column, defaults a fresh start to 2026-01-01, and otherwise begins at the day after the physical maximum. It schedules with `get_trading_dates_between`, which uses the complete SSE master calendar. It maps source `trade_date` to physical `timestamp`; pending DataFrames are grouped in batches of at most 20 dates. The Python max-date strategy has no revision overlap; D016 uses the common-contract receipt-backed five-calendar-day overlap instead.
- `ETFShare` declares model fields `ts_code`, `timestamp`, `fd_share`, and `update_time`; `update_time` is generated by `datetime.now` during model validation/write preparation. Its QuestDB schema declares six physical columns: `ts_code SYMBOL`, `timestamp TIMESTAMP`, `fd_share DOUBLE`, `fund_type STRING`, `market SYMBOL`, `update_time TIMESTAMP`.
- The shared Python serializer calls `prepare_questdb_dataframe`, validates model fields, and preserves a schema column that the model does not define only when that column is present in the incoming DataFrame. `_preserve_existing_columns` has the same source-DataFrame-presence condition. The D016 Python sync neither joins `fund_basic` nor enriches `fund_type` or `market` before calling `write_model`; static inspection alone did not establish which extra provider fields the no-`fields` Python call returns.
- `fund_basic` does expose a current `fund_type`, but it does not provide a historical `fund_type` as of each `trade_date`. D016 does not join that current-state table or claim point-in-time classification. There is no evidence in the D016 Python call path that it is the authority for historical `etf_share.fund_type`.

## Official source contract

Tushare [`fund_share` documentation, doc 207](https://tushare.pro/document/2?doc_id=207), checked 2026-09-30, states that a response is capped at 2,000 rows, documents `trade_date` and a `market` filter (`SH` or `SZ`), and lists `ts_code`, `trade_date`, and `fd_share` as output fields. It does not describe offset/limit paging or a total-row bound beyond the per-response maximum. A live, read-only explicit-field diagnostic on 2026-09-28 also showed that `fund_type` and `market` are accepted output fields: SH returned 1,001 rows with 940 nonnull `fund_type` values and `market=SH` on all rows; SZ returned 775 rows with 747 nonnull `fund_type` values and `market=SZ` on all rows. Requesting `update_time` failed with a safe Tushare `CONTRACT` error on both markets. Bounded evidence: `artifacts/java-migration/D016/provider-diagnostic/etf-share-field-probe-20260928-d15d24be-b894-4c7f-b849-d90750321f09.json`. Each candidate was requested separately, so the production five-field combined projection still needs a live run acceptance.

The Python call has no market filter, and the official docs mention only SH/SZ. A later read-only provider scope probe found an undocumented but supported `market=O` partition: on 2026-09-17 the unfiltered five-field response returned 1,774 rows split exactly into SH=999, SZ=766, O=9, and the explicit O query returned those same nine `.OF` codes. Evidence: `artifacts/java-migration/D016/provider-diagnostic/market-scope-e00c525f-97f9-483e-89b2-dff1562f460b.json`. Java therefore makes three bounded requests per SSE-open date (`SH`, `SZ`, `O`); any 2,000-row response fails closed, giving a local ceiling of 5,997 rows/date. Six-digit `.OF` codes map to provider market `O`. No undocumented paging parameters are injected. It rejects duplicate complete keys across all three partitions, suffix/partition/market mismatches, date drift, missing/extra output columns, and any failed/unknown request. `sourceVersion` is recorded as null because the source response exposes no snapshot token.

The live explicit-field diagnostic establishes that `fund_type` is nullable provider data and `market` is a provider field; Java requests both and cross-checks provider market against its partition and code suffix (`.OF`→`O`). `fund_type` is not declared in the Python `ETFShare` model, but the generic writer can preserve the incoming column if the DataFrame carries it; the Python no-`fields` response was not captured here. Java continues to freeze `update_time` from `observedAt` because Tushare rejected that candidate field. A bounded read-only query of the existing `etf_share` table found `fund_type`: null 162,420; `ETF` 159,375; `CEF` 4,600; `(带固定封闭期)` 1. The table's `market` values were `SH` 132,478; `SZ` 117,867; null 75,406; `O` 645. Explicit provider values now provide a source basis for correcting same-key legacy `fund_type`/`market` values during isolated acceptance.

## Pending provider-field diagnostic

The shared Java request path cannot issue a request with empty `fields`: `TushareRequest` rejects an empty list, `PageContract` requires nonempty declared fields, and `TusharePageService.fetcher` always sends `contract.fields` through `TushareClient`. Therefore it cannot test whether Tushare returns its full default projection when `fields` is blank/omitted. `EtfShareProviderFieldsDiagnostic.probe(LocalDate, BooleanSupplier)` used the shared budget for at most six explicit-field reads (SH/SZ × `fund_type`, `market`, `update_time`) on the same date with the three documented fields also requested; it did not write QuestDB or serialize a token. Empty-response schemas are not observable through the current service abstraction because it returns rows but drops the response field list when there are no rows. The D016 source now uses the provider-confirmed explicit five-field projection rather than relying on the untested default projection.

The write port treats provider `fund_type=null` as a source revision and uses the Java sender's documented omitted-setter SQL NULL representation; DEDUP UPSERT plus full-row readback must prove that a prior nonnull value was cleared. Provider `market` is required and checked against both the request partition and suffix mapping, so actual source values may correct prior legacy values. Job version 3 invalidates the earlier two-partition receipts; the old v2 isolated target must not be reused as a checkpoint. Incremental planning requires a same-target v3 verified receipt chain and reconciles every existing key/value against the newest valid same-target v3 receipt per date across INCREMENTAL/BACKFILL/RECONCILE, while only INCREMENTAL receipts advance checkpoint. Formal-table DDL is not added; only a caller-created `java_d016_etf_share_*` acceptance table is supported.

## Read-only physical schema check

Only bounded SELECTs were issued to the local QuestDB HTTP query endpoint:

```sql
SELECT "column", "type" FROM table_columns('etf_share') LIMIT 20;
SELECT ts_code, timestamp, fd_share, fund_type, market, update_time
FROM etf_share ORDER BY timestamp DESC, ts_code LIMIT 5;
SELECT fund_type, count() AS rows FROM etf_share GROUP BY fund_type ORDER BY rows DESC LIMIT 20;
SELECT market, count() AS rows FROM etf_share GROUP BY market ORDER BY rows DESC LIMIT 20;
```

The schema returned exactly `ts_code SYMBOL`, `timestamp TIMESTAMP`, `fd_share DOUBLE`, `fund_type STRING`, `market SYMBOL`, `update_time TIMESTAMP`. A recent sample carried six-digit exchange-qualified code, `fd_share`, `market=SZ`, and a UTC-rendered `update_time` with microseconds. Both stored timestamps are QuestDB `TIMESTAMP`, so the Java storage contract uses microsecond precision. The `trade_date` column is a business date carried at UTC midnight in `timestamp`; `update_time` is a frozen technical observation instant, not a provider revision timestamp. The formal table was only read and was not modified.

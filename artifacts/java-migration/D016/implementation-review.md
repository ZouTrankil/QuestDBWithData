# D016 `etf_share` implementation review

Implementation status: `implemented_not_verified`. The coordinator accepted earlier D016 v2 SH/SZ runs, then a read-only 2026-09-17 provider scope probe found nine additional O-market rows. This source-scope/job-v3 change has not yet been compiled or used for QuestDB writes.

## Added Java surface

- `TushareEtfShareDto`, `EtfShare`, `EtfShareKey`, `EtfShareDataset`, and `EtfShareMapper` define the full six-column storage contract and explicit five-field source projection (`ts_code`, `trade_date`, `fd_share`, `fund_type`, `market`). `trade_date` maps to a business-date carrier in physical `timestamp`; physical TIMESTAMP values use microseconds. `market` is preserved from provider and checked against the requested partition; `.SH`/`.SZ` map directly and `.OF` maps to provider market `O`. `fund_type` is preserved as a nullable provider value, including explicit null revisions. `update_time` stays frozen from `observedAt` because provider rejected that candidate field.
- `EtfShareReadRepository` performs bounded typed key and half-open range reads over all six fields.
- `EtfShareWritePort` caps QWP batches at 250 rows/1 MiB, checks expected isolated target identity before and after preflight/readback, separates ACK from full-key/full-field readback, and reconciles at most 10,000 distinct dates and at most 5,997 rows/date. It treats nullable `fund_type` and provider `market` as authoritative full-row source fields; sender omission for null must be proven by full-row readback on updates.
- `EtfShareSource` uses the shared rate-limited `TusharePageService` and one single-response call for each SH/SZ/O market partition per frozen SSE session. Although O is not listed by the official filter docs, read-only source evidence on 2026-09-17 proves unfiltered 1,774 = SH 999 + SZ 766 + O 9, and an explicit O call returned the same nine `.OF` codes. At-cap responses, missing/extra fields, malformed values, duplicates, out-of-partition symbols, date drift, source errors and cancelled calls fail closed. Complete receipts have canonical ascending `ts_code` order inside SH, SZ, then O, declared source field order, exact request parameters, per-market counts, raw rows, frozen observation time and SHA-256 fingerprint. Incomplete responses preserve attempted requests and captured rows as unverified evidence.
- Receipt serialization is deterministic across JVM runs: `JobDefinitionJson.mapper()` returns a fresh mapper, map-key sorting is disabled locally, and receipt maps are created as `LinkedHashMap` in fixed field order. Source response rows are reprojected by `orderedRow` to `EtfShareMapper.SOURCE_FIELDS` before sorting by `ts_code`; SH/SZ/O request and market order are fixed. The incomplete-evidence `capturedResponses` maps were also changed from `Map.of` to ordered maps so this guarantee does not depend on immutable-map iteration order.
- `EtfShareProviderFieldsDiagnostic` ran read-only on 2026-09-28: fund_type support and nullable counts were confirmed on SH/SZ, market was accepted, and update_time returned Tushare CONTRACT failures. Separate 2026-09-17 market-scope evidence proves nine nonempty O rows. The combined five-field, three-partition production source still requires live v3 acceptance. Empty `fields` remain unsupported by the shared transport.
- `EtfShareSyncAdapter` freezes and rechecks sorted SSE calendar dates, uses one ledger slice/receipt per trade date (containing all three market responses), honors cancellation, and marks dates verified-empty only after all three requests complete below cap.
- `EtfShareSyncJobOwner` declares job version 3 (the earlier two-partition v2 is not checkpoint-compatible), `data.etf_share`, `etf_share.trade_date`, incremental/backfill/reconcile modes, 366-calendar-day windows, 5-day revision overlap, at most 3 source requests and 5,997 returned rows per date, and exchange-calendar dependency.
- `EtfShareCoverage` advances only same-target verified INCREMENTAL v3 runs with the frozen bootstrap anchor and exact per-date receipts; BACKFILL/RECONCILE never advance the checkpoint. Physical-value validation overlays the newest verified same-target v3 receipt by date across all modes, ordered by summary `updatedAt` and run ID only as a stable tie-breaker. It compares every row/value including `update_time` and fails on unexplained dates or mismatches.
- `EtfShareJobService` requires `java_d016_etf_share_<suffix>`, freezes target identity and physical range in the request, requires an explicit bounded bootstrap `--from` without a receipt-backed checkpoint, applies completed-source end-date resolution, includes actual physical rows in checkpoint reconciliation, validates the baseline again before a fresh run, exposes plan/run/resume/status/entries/cancel, restores old frozen requests for recovery, and does not inherit the old run's cancellation flag.

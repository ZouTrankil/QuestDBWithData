# D013 `etf_basic` source contract review

## Python call chain and endpoint contract

The Python connector is `src/quant_platform/data/adapters/connectors/etf/etf_basic_sync.py` in `D:/work/fund_2/back-monitor`. Its `_get_etf_basic` is decorated `api_limit=20, period=60`; the call is a single `pro.fund_basic(market='E')`. It does not pass `status`, `ts_code`, or a paging argument. The sync upserts rows it receives and does not delete codes absent from a later response. It normalizes only `""`, `"Null"`, and `"null"` to null for the seven date fields.

The official [Tushare `fund_basic` documentation](https://tushare.pro/document/1?doc_id=19) lists `market`, `status`, and `ts_code` filters and a maximum response of 15,000 rows. It does not document an offset, cursor, or continuation token. D013 therefore freezes one unfiltered `market=E` call. It does not split on D/I/L status: the local read-only target inventory has null-status records, and status filtering would omit them. Exactly 15,000 rows is treated as possibly truncated: the untouched response is recorded as `unverified_raw_response` and no row is emitted to the writer. A zero-row market-wide response is recorded and rejected rather than interpreted as authoritative deletion or a useful empty snapshot.

## Frozen source fields and mapping

The source response is required to contain these 25 fields, in the declared projection order:

`ts_code`, `name`, `management`, `custodian`, `fund_type`, `found_date`, `due_date`, `list_date`, `issue_date`, `delist_date`, `issue_amount`, `m_fee`, `c_fee`, `duration_year`, `p_value`, `min_amount`, `exp_return`, `benchmark`, `status`, `invest_type`, `type`, `trustee`, `purc_startdate`, `redm_startdate`, `market`.

The Java DTO contains exactly those source fields; it does not claim `timestamp` or `update_time` came from Tushare. The mapper preserves text, parses the seven exact `YYYYMMDD` date strings to `LocalDate` (including the Python null sentinels), and parses the seven numeric fields to finite `Double` without rescaling. `market` must equal `E`; `status` preserves null or D/I/L. The `ts_code` key retains the complete exchange suffix, including `.OF`.

The audited physical table has 27 columns: those 25 plus `timestamp TIMESTAMP` and `update_time TIMESTAMP`. Its designated timestamp is `timestamp`, partition is YEAR, WAL is enabled, and dedup key is `(ts_code,timestamp)`. `timestamp` is the fixed UNIX epoch technical carrier for the Python model's `datetime(1970,1,1)` default; it is never treated as a business date or source watermark. `update_time` is generated by the Python model rather than returned by `fund_basic`; Java freezes one UTC microsecond `observedAt` per plan and reuses it on resume. A fresh snapshot gets a fresh observation instant. This makes response-to-row mapping deterministic for a frozen run while marking when Java observed the row, not when the provider revised it.

## Boundedness and data-retention policy

There is no date-key checkpoint or date overlap for this object: the endpoint exposes no source update cursor and every complete snapshot request rereads the bounded market directory. The weekly job is explicitly `SNAPSHOT`; it uses a complete-source receipt and frozen observation time instead of advancing the misleading 1970 timestamp. On each accepted run, returned codes are upserted by the audited physical key. Codes absent from the response remain in QuestDB because absence in one directory response is not a deletion instruction. A source status D row is retained as data. No formal-table DDL or Flyway migration is added; only a D013-prefixed isolated target may be created for acceptance.

Each valid source response is capped to one unpaged request and saved as a canonical raw receipt before writing. Responses are sorted by full `ts_code` for stable receipt/fingerprint identity; duplicate keys, missing declared fields, out-of-scope market, invalid status/date/numeric values, cancellation, request errors, and cap hits fail the run. A valid response is split only after source completion into runner pages of at most 10,000 rows, then into verified writer batches of at most 250 rows and 1 MiB. Every batch uses full-key/all-column readback and WAL-settlement checks through the shared runner.

## Local audit evidence and limitations

The read-only QuestDB inventory performed during implementation found the audited `etf_basic` target with 2,958 rows, all at `1970-01-01`, 27 physical columns, YEAR/WAL/DEDUP, and `(ts_code,timestamp)` upsert key. Its E-market status counts included 43 null values, 680 D and 2,235 L; this is why status partitioning is not used. The observed `update_time` values were non-epoch. This inventory is schema/source-contract evidence only; it is not D013 source-to-isolated-target acceptance.

No live Tushare request, QuestDB write, build, or test was run for D013. Python's 20/minute decorator is source evidence, not the authenticated account's current quota.

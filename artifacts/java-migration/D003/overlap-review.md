# D003 candidate-file overlap and revision boundary

Read-only comparison of the 17 normalized source fields in `source-catalog.csv` with the 2,274-row QuestDB `index` baseline produced [overlap-analysis.json](overlap-analysis.json). The candidate file has 2,343 unique codes: 1,814 overlap, 529 are absent from the current table, and 460 current codes are absent from the candidate. Every overlapping row differs in `latest_close`; 1,809 differ in `return_1m`, and 970 differ in `sample_count`. Import time was excluded because it is a local observation, not a source revision field.

The file's exact April import identity is unproven, and it does not declare the market date for `latest_close` or `return_1m`. The 460 target-only codes require explicit retain or remove semantics. Existing `index` is WAL, MONTH partitioned and has no dedup key, so appending changed rows under a new import time would leave multiple physical rows per `index_code`; an ACK or row-count increase would not prove a current-row revision. The D003 writer must choose and verify a publication/identity policy before accepting these 1,814 revisions. No production writes were made for this comparison.

The Java typed read and read-group test passed against existing QuestDB rows. `local-D003-read-merge` also loaded all 2,274 physical rows with identity and WAL preflight, parsed the 2,343-row candidate, and calculated a 2,803-row merged snapshot: 529 inserts, 1,814 revisions, 460 retained absent codes and 0 unchanged overlapping rows. The bounded file parser suite passed (`local-D003-source`, 4 tests). `local-D003-stage-ours` staged and read back all 2,803 rows in an isolated WAL table. The independent [stage comparison](stage-7bbdfd20-fed8-4867-9864-2e6fbe28ee4e/independent-stage-values.json) matched all 2,343 source keys and 17 source fields, and retained the other 460 rows unchanged. Production identity and rows stayed unchanged. Publication and owner-run acceptance remain outstanding.

`local-D003-wal-swap` cloned the complete catalog into a test-owned WAL table, waited for the CTAS WAL to settle, staged the 2,803-row merge, renamed the old clone to backup and the verified stage into its name, and checked both physical identities, all rows and both fingerprints. Successful test tables were dropped. An earlier clone left by an immediate WAL-preflight race was checked by exact table ID 2208 and dropped after the wait fix. This proves the isolated physical swap path; durable interruption recovery and owner-run acceptance remain outstanding.

`local-D003-publication-current` passed both normal publication and an injected `Error` after the first rename. Its journal detected `OLD_MOVED` and required stopped-writer proof before completing the second rename. A separate observed failed probe from `local-D003-publication` was recovered by `local-D003-observed-recovery`; [the receipt](observed-recovery.json) records the exact test run, published and backup identities and row counts. Only that probe's two test tables were dropped after recovery. Full catalog owner-run acceptance remains outstanding.

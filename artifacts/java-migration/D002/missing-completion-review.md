# D002 published recovery without completion receipt

Before staging starts, the owner now saves `prepared-publication.json` with its frozen run/request/target, complete original snapshot, source rows and receipt paths, observation time and intended merge. A failure to save this intent occurs before staging submission. No successful checkpoint is recorded at that point.

For a stopped RUNNING or IN_DOUBT owner whose completion receipt is absent, recovery recomputes the merge from that frozen input, requires a single owned publication intent, binds the current endpoint to the original physical target identity, and requires the exact PUBLISHED target/backup/stage layout. It then reads the whole actual target and compares every stored field to the intended merged rows before reconstructing `completion.json`. Normal source-key validation and ledger completion follow. Existing malformed completion files are not silently replaced. An unpublished or conflicting layout is rejected by this path.

`local-D002-missing-receipt-cc5e` passed StockDetailSliceRecoveryLiveTest with a real Tushare code and isolated QuestDB table. The test first rejects the slice completion transaction after publication, preserving three IN_DOUBT ledger entries. It then moves the original completion receipt to an explicitly named test backup to simulate the missing-file boundary, without changing ledger states. Recovery rebuilds the missing receipt from prepared evidence and live readback, verifies all three ledger levels, releases the retained lease, and leaves the target identity and every row unchanged. Successful test target and publication backup were subsequently dropped.

This is a simulated missing-receipt boundary, not an OS-process-kill test. The test proves published recovery without the final receipt. Restoring an unpublished two-rename layout remains the separate publication restoration operation; final owner/task recovery integration must still be audited before D002 closure.

# D002 prepared static write group

The existing prepared writer accepts only WAL tables with a designated timestamp and physical deduplication key. `stock_detail_info` is an unpartitioned non-WAL table with an application-enforced `ts_code` identity, so D002 uses a separate `STATIC_REPLACE` capability. The general append adapter remains restricted to WAL tables. The write-group parser and plan apply the same full-column, complete-key, 10,000-row and 16 MiB limits before admitting a static member.

`StaticStockDetailWriteAdapter` freezes the prepared request and row fingerprint, persists the exact typed input receipt, and calls the canonical static owner. The owner acquires the whole-dataset lease, merges only changed business values, writes an owned stage in 250-row batches, verifies all 18 physical columns, publishes with a durable journal and retained backup, then reads the final complete table before marking the child run verified. The parent uses the existing `PersistentWriteGroupRunner` ledger. Static replacement must be the final member in a write group, so a later member cannot fail after a verified replacement changes the target identity. A prior FAILED/CANCELLED static member can be replayed only when it has no publication evidence or retained lease; an uncertain member requires explicit reconciliation.

`local-D002-static-write-live` passed against a test-owned QuestDB table. The source row came from a read-only physical production snapshot; no Tushare request is claimed for this prepared path. First write published one row; the identical second write-group run verified the same row without a second replacement. Parent and child entries in both runs are VERIFIED. Exact business values matched, and the production table identity and fingerprint were unchanged. The successful test table and backup were removed after the evidence was saved. See `write-group-*/prepared-write.json`, `write-group-*/write-group-readback.json` and the corresponding `var/sync-evidence/<child>/completion.json`.

The group is serial and has no cross-table atomic transaction. A completed static group should be run anew for a later batch; a resume from its old pre-publication target identity is rejected. This is intentional target-drift protection, not an omitted write.

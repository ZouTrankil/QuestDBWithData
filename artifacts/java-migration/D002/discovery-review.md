# D002 bounded market discovery and read-only physical comparison

Status: source and physical-read evidence only. No D002 target write or publication is claimed here.

`StockDetailInfoDiscovery` requests `stock_basic` for L/D/P × SSE/SZSE/BSE, preserving a separate source receipt per slice. It requires every slice to return below the official 6,000-row cap, rejects out-of-slice/duplicate identities, and bounds the aggregate to 10,000 keys. The source is used for new-identity discovery and reconciliation; exact-code `StockDetailInfoSource` remains available for a bounded known-code refresh.

The first static test run (`local-D002-discovery-static`) failed because its synthetic cap-sized page repeated one key and hit duplicate-key validation before the truncation guard. The fixture was corrected to 6,000 distinct synthetic keys. `local-D002-discovery-static-b` then passed 3 tests: nine-slice completion, cap-sized/duplicate rejection, and empty/wrong-exchange rejection.

`local-D002-discovery-live` passed 1 opt-in test in 59 seconds against actual Tushare. It returned 5,910 unique L/D/P identities across nine requests, with maximum slice 2,903 rows; P was empty for all three exchanges at this observation. All nine raw source receipts and `discovery-validation.json` are under `discovery-1755c630-c3ad-4ca1-af0a-6db96da7e2e3/`. The test performed zero writes.

An independent read-only PGWire `SELECT` of all 17 business fields from the current `stock_detail_info` table, using `tools/compare_stock_detail_discovery.py`, compared the retained source responses by full `ts_code` identity. The first script attempt included `discovery-validation.json` in a broad file glob and failed before querying. After narrowing the glob to the nine status receipts, the comparison succeeded: 5,910 source keys, 5,908 target keys, 5,908 shared, 5,892 business-value matches, 16 changed, 2 source-only (`301716.SZ`, `920202.BJ`), and zero target-only. The source differences affect `act_name` (10), `act_ent_type` (1), `name` (4), `cnspell` (4), `fullname` (1), `enname` (2), and `industry` (1); one key can differ in multiple fields. The full field and count evidence is `physical-compare.json` in that folder. `update_time` was deliberately excluded because it is a local observation timestamp rather than a Tushare business field. Existing literal date `None` was normalized only for this comparison, with original raw values retained.

The official [`stock_basic` interface page](https://tushare.pro/document/1?doc_id=25) states the per-call 6,000-row limit and supports status/exchange filters. The Python owner scope is L/D/P; the page also describes G/UN statuses, which are not silently added to this migration.

The physical comparison demonstrates real candidate inserts/revisions for isolated acceptance. It does not prove the Java owner applied them, the non-WAL stage was safely published, or the resulting table was re-read. Those remain D002 gates.

Subsequent `local-D002-full-stage-live` passed one opt-in integration test: it repeated all nine real source requests, read the 5,908-row production table without mutation, merged 2 inserts and 16 business-field revisions while preserving 5,892 unchanged rows, and wrote all 5,910 rows to an owned isolated non-WAL stage. The stage's physical 18-column readback exactly matched the prepared rows; the production table identity and fingerprint stayed unchanged. The successful stage table was dropped after saving `full-stage-*/full-stage-readback.json`, source receipts, stage intent and verified snapshot. This establishes full bounded source→isolated stage→QuestDB readback; publication/rename and owner checkpoint remain separate gates.

An independent comparison using `tools/verify_stock_detail_stage.py` then read the nine raw source receipts and the retained actual QuestDB stage snapshot. `full-stage-d4468272-cb26-4a57-a711-32720821dc85/independent-stage-values.json` records 5,910/5,910 matched `ts_code` keys, zero missing/extra keys and zero mismatches across all 17 source business columns. Legacy date sentinel `None` is normalized explicitly; physical `update_time` is excluded because it is generated locally and was already checked by the Java stage equality test.

# D011 source and storage contract — `stk_suspend`

## Source and normalization

- Source endpoint: Tushare `suspend_d`, called with exactly one `trade_date=YYYYMMDD` and `suspend_type=S` per daily slice. The official [suspend_d documentation](https://tushare.pro/document/2?doc_id=214) supports date/code parameters, returns `ts_code`, `trade_date`, `suspend_timing`, and `suspend_type`, and caps a single query at 5,000 rows.
- Source fields are strict: `ts_code` and `trade_date` are required business-key values; `suspend_type` must be `S`; `suspend_timing` is nullable evidence retained in raw/normalized receipts but is not a stored column. Rows with invalid codes, a date outside the frozen daily slice, a different type, duplicate `(ts_code,trade_date)` keys, or a response at the 5,000-row cap are rejected. Cap-hit raw rows remain marked unverified evidence.
- The Python caller in `D:/work/fund_2/back-monitor/src/quant_platform/data/adapters/connectors/stock/price/stk_suspend_sync.py` walks trading dates, requests `suspend_d(trade_date=..., suspend_type='S')`, and normalizes every returned S row to `is_suspended=1`, `timestamp=trade_date`. The Python helper retries some source failures and de-duplicates duplicate codes by keeping the last row; Java instead rejects duplicate keys so ambiguous input cannot be silently discarded.
- `suspend_timing` documents optional intraday windows such as `09:30-10:00`; a row with `suspend_type=S` means a suspension applies on the date, not necessarily a full-day halt. Java preserves timing in evidence and writes `is_suspended=1` without claiming a full-day suspension. `R` resume rows are excluded by the explicit `S` request and cannot be mapped as suspension rows.
- The physical table has exactly three columns: `ts_code SYMBOL`, `is_suspended LONG`, and `timestamp TIMESTAMP`. Mapping is `suspend_d.ts_code → ts_code`, derived `suspend_d.suspend_type=S → is_suspended=1`, and `suspend_d.trade_date → timestamp` as a UTC-midnight business-date carrier. There is no event-time interpretation or numeric unit conversion.

## Physical shape and isolation

- The 2026-09-29 audited object dictionary records `stk_suspend` as `timestamp`-designated, DAY-partitioned, WAL-enabled, `DEDUP UPSERT KEYS(ts_code,timestamp)`; Python's `StkSuspend.get_questdb_schema()` declares YEAR partitioning. Java preserves the audited physical DAY shape and does not modify production DDL or add a Flyway migration.
- Live acceptance must use the explicit isolated target `stk_suspend_d011_isolated` with the same three-column DAY/WAL/dedup schema. The D011 owner preflight rejects schema/target drift; it is non-creating and non-repairing.
- Business identity is `(ts_code,trade_date)`; physical identity is `(ts_code,timestamp)`. The mapper uses a `LocalDate` business date with the repository's calendar timestamp carrier. Readback compares the full stored row by the complete key.

## Bounded incremental plan and recovery

- Default mode is `INCREMENTAL`. The first plan requires an explicit bootstrap start and is capped at five calendar days, including any later physical `MAX(timestamp)` catch-up ceiling. A physical maximum does not establish verified coverage; dates after the frozen `logicalDate` are rejected.
- Later plans resume only from contiguous receipt-backed `VERIFIED` or `VERIFIED_EMPTY` incremental coverage for the same isolated `targetId`, job/schema version, and bootstrap anchor. They re-read the checkpoint date and two preceding calendar days (`revisionDays=2`) and advance no more than two calendar days per verified run. `BACKFILL`, failed, partial, and in-doubt runs never advance the checkpoint.
- Each calendar date produces its own raw source receipt, including an empty response. A checkpoint requires exactly one verified date-slice receipt for each date in the frozen interval; a verified-empty date is a real no-row source response, not a synthetic row or an omitted request.
- Every source page is buffered with its raw receipt before the runner accepts it. The job then stages the entire inclusive `[from,to]` window as the exact authoritative S-row set plus unchanged rows outside the window. The runner's per-slice QWP writes and full-key readbacks target only that verified stage; the logical table remains unchanged until publication. This removes revoked keys without inventing `is_suspended=0` tombstones, and an authoritative empty source window clears stale positives.
- The replacement stage has a bounded full-target snapshot and readback; outside-window rows must match the pre-fetch snapshot exactly. Publication uses a D011-specific cross-process exclusive lock, a durable journal, and two QuestDB table renames. A restart inspects target/backup/stage identities and resumes only recognized layouts; conflicts remain fail-closed. A frozen stable logical target and frozen physical generation are both checked; the journal plus a full stage fingerprint is required to authorize the new physical identity chain.
- If a stopped process leaves an all-empty source run after the rename journal was created, recovery revalidates every raw daily receipt, the full post-publication snapshot, and a strict all-zero verification proof before transitioning the run to `VERIFIED_EMPTY`. Nonempty/incomplete source pages cannot use that recovery path.
- Resume request identity uses the canonical request fingerprint plus the stable target identity, so JSON map/set iteration order across JVMs cannot make an otherwise identical frozen request appear different. Checkpoint definition matching uses record equality, including set semantics for supported modes and parameter choices.
- `targetId` is frozen into the planned request, checked after target-range reads, rechecked before execution, and passed to the writer for checks around write/readback. Batches are capped at 250 rows and 1 MiB; unknown QWP acknowledgements are reconciled by full-key reads and are never auto-replayed.

# 项目结构与开发规范

这篇给开发者和后续接手的 AI 看。业务按 A 股、美股、BTC 分目录；A 股数据和 Batch 共用市场常驻入口，主策略和实时 L2 独立启动。美股和 BTC 的基础行情使用各自有限采集入口，完成范围以来源和实库回读为准。

## 怎么用这份规范

开始改代码前，先读 [AGENTS.md](../AGENTS.md)，再看这篇和[相关功能说明](README.md)。用户当前明确提出的要求优先。

具体字段、命令和运行能力要对照代码、维护中的数据契约和实际验证结果。建好模块不代表来源已接通，旧运行记录也不代表当前已经就绪。

## 现在的模块

实际项目清单看 [settings.gradle](../settings.gradle)。顶层业务工程只有 `platform` 和 `markets` 两个父工程，子模块隔离市场职责、数据库驱动和批处理依赖：

```text
QuestDBWithData/
├── platform/                       公共父工程，只聚合构建
│   ├── core/                       纯 Java 通用模型、契约和时间接口
│   ├── runtime-support/            配置、日志、启动和时钟装配
│   ├── app-support/                公共 Web/API 支持库，没有启动入口
│   └── engine/                     通用请求、配额和分页
│       ├── source/                 来源契约、采集和市场注册
│       ├── questdb/                数据读写、核验和恢复
│       └── batch/                  Batch 元数据、写入和 Quartz 支持
├── markets/                        市场父工程，只聚合构建
│   ├── cn/                         A 股模型和共享字段
│   │   ├── source/                 A 股和中国宏观来源
│   │   ├── data/                   清洗、同步、特征和市场 API
│   │   ├── data-app/               A 股入口，常驻时托管 Batch
│   │   ├── batch/                  盘后任务、离线 L2、管理和调度
│   │   ├── main-strategy-runtime/  主策略独立入口
│   │   └── l2-live-app/            实时 L2 独立入口
│   ├── us/                         美国表投影、利率来源、行情定义和时间入口
│   │   └── data-app/               美股独立有限采集和正式写入入口
│   └── btc/                        BTC 时间、币价定义和来源映射
│       └── data-app/               BTC/ETH 现货与永续有限历史采集
├── config/                         公共、市场和应用配置
├── docs/                           规范和使用说明
├── deploy/                         部署脚本与示例
├── tools/                          生成与检查工具
└── build/                          全部构建产物
```

`markets/cn/data` 与 `markets/cn/batch` 分开，Batch 库自身不依赖 PGWire、QuestDB Sender、POI 和数据 API。统一市场发行包同时包含数据与 Batch 的依赖，Batch 使用独立 Spring 容器，SQLite 数据源和事务不与 QuestDB 混用。实时 L2 只使用 core 和启动支持，不加载整个 A 股业务库。

根工程不放生产代码，只做聚合检查和兼容打包。`platform`、`markets` 也不放源码或业务 jar；`engine` 和 `cn` 继续保留原有模型或执行代码及子模块。Gradle 使用完整路径，例如 `:markets:cn:main-strategy-runtime`；根级 `mainStrategyRun`、`aliyunL2Live` 等启动命令继续保留。

## 代码应该放哪里

- **platform/core**：跨市场通用模型、数据契约、业务键、时间范围和市场时间接口。主代码只用 JDK，不引入 Spring、Jackson 或数据库。
- **platform/engine**：通用执行、分页、配额、来源归档、读写核验和恢复。市场通过接口注册规则，引擎不能反向调用市场实现。
- **市场模块**：表模型、来源字段、单位、日期规则、清洗、特征、质量检查和应用。美国利率不能因为被 A 股使用就搬进 A 股清洗代码。
- **platform/app-support**：公共鉴权、数据目录查询/导出和 schema 迁移配置。它是库，没有 main 方法，不依赖任何市场；市场应用按需导入 `DataApiConfiguration`。实际数据库操作在通用引擎，迁移 SQL 跟着所属市场维护。
- **市场应用入口**：放在各市场目录下，负责参数、市场 API/CLI 分发和组件装配。A 股、美股、BTC 分别使用 `markets/cn/data-app`、`markets/us/data-app`、`markets/btc/data-app`；有限采集入口不加载 A 股或 L2。
- **platform/runtime-support**：配置、日志、网络和启动支持。有限 CLI 不顺带启动调度、采集或其他常驻服务。

依赖方向是“市场运行入口 → 市场业务 / 公共 API 支持库 → 通用引擎 → core”。市场之间读取明确的数据产品，不互调清洗或策略实现。主策略直接使用 A 股业务库，不依赖 `markets/cn/data-app` 的入口 jar。公共 `platform/app-support` 是可复用的库。

市场的数据目录说明通过 core 的 `DataCatalogProvider` 接口和 `META-INF/services` 注册。公共 API 只发现当前 classpath 中的说明，不硬编码 CN/US/BTC 实现。没有市场登记时也能展示实库元数据，缺少说明的对象标为未分类；没有读取实现时不宣称支持读取。

来源规则通过 `SourcePolicyProvider` 注册；A 股和美国各自提供实现和资源。通用 `SourceContract`、采集器与账本继续复用。未知来源或重复注册直接报错，不提供猜测性的兜底。

迁移保留了已有 Java 类名、表名、数据集版本、任务 ID 和实例身份算法，特别是 Quartz 中已经保存的作业类名。老包名不是业务归属依据；新代码先按市场和功能找目录。

## 按功能分包

先按 `stock`、`etf`、`index`、`l2`、`factor`、`strategy` 等功能分，再在里面分层：

| 子包 | 放什么 |
| --- | --- |
| `domain` | 数据、业务键和纯规则 |
| `application` | 同步、校验、取消、恢复等流程 |
| `port` | 流程需要的读取、写入和会话接口 |
| `mapper` | 来源、业务和存储字段之间的转换 |
| `storage` / `client` | SQL、文件、数据库和外部接口访问 |
| `config` / `bootstrap` | 配置绑定、组件装配和资源关闭 |

domain 不依赖应用或存储；port 不引用具体实现；mapper 不访问网络、数据库，也不靠当前时间改变结果。CLI/Web 调应用服务，不直接碰数据库。

一次运行的 writer、session、取消标志、未决状态和临时表绑定要单独创建，不能作为共享单例。不可变定义和纯函数可以共享。

兼容代码保留现有包名。新增市场代码用 `com.zoutrankil.market.cn`、`.us`、`.btc`。迁包时不要顺手改任务身份、表名或恢复流程。

CN 共享模型在 `com.zoutrankil.data.domain` 下按数据类别归组，股票再细分基础、行情、财务等；分类与生成规则见[模型目录](model-schema-conventions.md#模型目录怎么分)。跨模块引用使用实际模型包，不恢复根目录平铺；市场归属仍由模块和显式契约决定。此次模型迁包的边界见[设计决定](decisions/2026-10-19-CN模型分类.md)。

## 时间怎么处理

| 时间含义 | 写法 |
| --- | --- |
| 真正发生的时刻，如成交、采集、公告可用时刻 | `Instant`，统一存 UTC |
| 交易日、报告期、上市日 | `LocalDate`，不加减时差 |
| 没有偏移量的本地时间 | 先说明来源时区，再转成 `Instant` |

A 股业务日和会话用 `Asia/Shanghai`。美股交易日和会话用 `America/New_York`，按交易日历处理夏令时，不能固定写成 UTC 某个小时。BTC 默认 UTC，交易所另有日线切分规则时按来源约定。

所以，美股和 BTC 的事件也统一存 UTC，但“哪天开盘”由各自的业务规则决定。美国宏观发布日期不套用美股交易日历。

现在用 `MarketId`、`MarketTime`、`MarketClock` 和 `MarketTimes` 明确区分三个市场，由 `platform/runtime-support` 从 `app.time.markets` 装配。A 股的旧 `BusinessTime` 继续适配同一个 A 股时钟，`app.time.business-zone` 只作为兼容配置，冲突时拒绝启动。JVM/JDBC 继续使用 UTC。

夏令时缺失或重复的本地时刻不自动猜测；重复时刻需要来源明确给偏移量。开市日仍查询版本化交易日历，不能用“周一到周五”替代。具体用法见[市场时间](market-time.md)，来源归属见[数据集归属](dataset-markets.md)。

**历史日期标记不要整体加 8 小时。** 例如 `2026-10-19T00:00:00Z` 可能只是“10 月 19 日”的编码；上海当天实际零点则是 `2026-10-18T16:00:00Z`。两者用途不同。重试继续使用原 `logicalDate`，不要重新取今天。字段精度也要固定，不能悄悄丢掉微秒或纳秒。

## 新数据先把约定写清楚

新增前说明：属于哪个市场、谁提供、谁唯一负责写、消费者是谁；字段类型、单位和空值是什么；业务键包含哪些维度；各时间字段表示什么；分页怎样结束；缺数据怎样判断；结果写哪里；失败怎样恢复。

来源 DTO、业务模型和存储行可以不同，用 mapper 明确转换。生成代码改维护中的契约或生成器后再生成，不直接手改生成结果。

保留证券前导零和交易所后缀。BTC 行情还要区分交易所、币对、现货或合约、计价币和周期。null、零、NaN、空串不能随意互换；排名、并列、浮点累计和精度按原规则处理。

数据库对象用 `snake_case`，原生物化视图用 `mv_<产品名>`。没有实际需要就不再套一层 `v_*`。也不要习惯性复制整套 `_v1`、`_v2` 类。已有持久化名称和版本要按迁移处理，不能批量改名掩盖不兼容。

具体步骤见[模型和新增数据集](model-schema-conventions.md)。

## Java、Python 和存储怎么分工

| 内容 | 负责方和位置 |
| --- | --- |
| 外部数据同步、QuestDB 建表和维护 | Java |
| 市场原始行情和共享时序产品 | 按数据约定放 QuestDB |
| 研究、训练、探索性回测 | Python，本地 Parquet / SQLite 等 |
| 已迁入 Java 的正式评分和输入产品 | 继续由 Java 生成，使用已验收的方案和训练文件 |
| 自有策略运行、订单、成交、持仓记录 | 本地 SQLite，不再建回 QuestDB |
| 实时 L2 解析结果、分钟数据和累计状态 | 类型化 Parquet |
| 实时 L2 原始接收日志、状态和提交引用 | SQLite |

Python 对 QuestDB 只读。同一个正式产物只保留一个写入方；正式评分或方案按现有 Java/Python 交接约定写入，不能只看文件在哪个仓库就决定归谁写。

Java 调用失败时，Python 不能偷偷启用另一套正式计算或写入。真实市场逐笔数据与自己的交易记录要分清。

实时 L2 备份、恢复要同时保留 SQLite 和它引用的 Parquet。MQTT QoS 0 丢失的输入不能补成“完整”。

## 增量、写入和恢复的底线

一次运行先固定来源、范围、版本和预算。来源分页结束、预期日期和证券覆盖都确认后，才能判断来源完整。历史修订、晚到公告也要有处理范围，不能只抓最大日期之后的数据。

发送前保存写入意图。写入后按完整业务键和字段值读回，检查 WAL 已应用、来源和目标版本稳定，再推进检查点。`MAX(date)`、行数相等、发送确认和进程退出码为 0，都不能单独证明完成。

结果不确定时保留原锁、来源和日志，先核对原运行与原物理对象；不能另开任务重发，也不能自动解锁。各业务已有状态机继续保留，不为了通用化合并不同的空源和恢复规则。

文件先写临时文件，校验后原子发布；成对产物和别名一起提交。不要在调用远端服务时一直占着 SQLite 写事务。删 stage/backup 前先确认归属、依赖和恢复用途。

删掉 `_meta` 表不代表增量已接管。每条源都要有新的完整性检查、写后核验和恢复记录。当前财务接管限制见 [QuestDB 维护](questdb-maintenance.md#五条财务增量接管)。

## QuestDB 和查询

建表用明确 SQL；已执行的 Flyway 脚本不改，结构变化加新版本。任务自带的建表操作先验证对象归属和结构，不靠 JPA 自动建表。

表、普通视图和原生 MV 要分清。MV 的 JOIN 右侧历史修订不一定触发重算，需要明确的全量或范围刷新。输出通过核验前，不能更新证书或对外宣称可用。

查询要限制日期、行数和超时，JOIN 的来源也要有界。历史研究要区分“当时已经可用”和“现在看到的最新修订”；只固定今天的值，不能证明当时就知道。数值移植用独立参考结果核对，不拿同一实现自产的样本当证明。

## 配置、构建和中文注释

运行配置只维护根 `config/`：`application.yml` 放公共值和导入，`markets/` 放市场设置，`apps/` 放进程设置。入口自动选择 profile，公共库没有单独运行配置，未接通的应用不复制空配置。保留可修改的实际默认值和 Spring 标准覆盖方式，不复制真实凭据到文档或日志。账号、方案或源文件缺失时明确报缺失，不生成假输入。

有限 CLI 不顺带启动调度器。数据库直连代理例外只对指定数据库生效，不关闭全局代理。已有 SQLite 调度设置按管理操作修改，不能假定改 YAML 会重置它。

用 Gradle Wrapper 和 JDK 24。依赖版本跟随项目 BOM、锁文件及兼容检查。构建产物统一到根 `build/`；未来嵌套模块使用完整项目路径区分输出，不能只用末级模块名。

新增或修改核心逻辑时必须补齐中文注释，如算法、业务规则、时间边界、写入和恢复流程。用口语和短句，说清用途、原因和关键限制，不逐行复述代码。逻辑改了，注释同步改。翻译注释不改业务行为，技术名称保留原文。

## 怎么验证和交付

先弄清市场、时间、业务键、写入方和消费者，再改代码。保持现有任务、目标表和恢复协议；确实需要改变时，写清迁移影响。

| 改了什么 | 至少检查什么 |
| --- | --- |
| 文档、注释 | 内容、相对链接、命令和文件路径 |
| 业务逻辑 | 相关模块测试；覆盖缺失、重复、修订和重试等实际分支 |
| 包或模块依赖 | `architectureTest`、`verifyModuleBoundaries` 和受影响发行包 |
| 数据库结构、正式写入 | 对应环境的结构、完整键值、WAL、幂等和恢复验证 |

```sh
./gradlew architectureTest verifyModuleBoundaries
./gradlew verifyDependencyVersionCompatibility verifyBatchDistributionDatabaseDrivers
```

模块检查和字节码检查覆盖全部子项目，详见[检查范围](architecture-rules.md#自动检查)。文档修改不用默认启动全量测试或外部作业。

交付写清改了什么、验证到哪、还有什么缺口。编译通过、固定样本通过、真实来源通过要分别说明。已获授权的工作继续完成，不额外增加重复确认。

给后续 AI 的任务可以这样写：

```text
先读 AGENTS.md、项目规范和本功能说明。
本次市场、功能、输入和输出：……
业务日期和时区：……
唯一写入方、业务键、允许修改范围：……
需要保留的命令、表名和恢复行为：……
完成条件和验证方式：……
```

## 后续扩展

接入新来源时，同时更新所属市场的注册、资源、模型、时区和覆盖测试。美股全市场日历与 BTC 数据源要有真实输入和验收结果后再启用，不复制一套空任务。

已有策略与实时进程仍分别启动、停止和部署。持久化任务的类名或身份需要改变时，必须单独迁移，不能顺手改包。

涉及市场划分、依赖、时间、写入方、业务键、产物格式、恢复或对外接口的重要变化，要更新本规范。需要记录取舍时放到 `docs/decisions/YYYY-MM-DD-主题.md`，有实际内容再建文件。

构建输出为 `build/modules/<完整模块路径>/_output/`，父模块输出不会包含子模块输出，单独 clean 不会连带删除子模块。每个模块的 `verifyTestOwnership` 检查测试 class 和资源归属，聚合测试不能借用旧构建产物。

### 离线检查入口

运行 `python3 tools/run_offline_tests.py`，Windows 可用 `python` 或 PowerShell 包装脚本。覆盖当前全部模块，报告在 `.gradle/offline-checks/`，`latest.txt` 指向本次结果。真实来源和数据库验收另跑。

保留历史原件的对照验收运行 `./gradlew :markets:cn:data:retainedParityTest`；缺原件会报错，不能用普通离线通过代替。

新评分发布前必须核验独立批准的来源范围清单，不能仅凭日期和当前行数标记完整。见[设计决定](decisions/2026-10-17-评分来源清单.md)。

## 本轮运行约定

公开默认值仍统一在根 `config/`，由 `application.yml` 导入 `markets/` 和 `apps/`；私密覆盖在被 Git 忽略的 `config/application-local.yml`，不随发行包分发。财务日批只在指定数据 API 持久进程启用，主策略和有限 CLI 不启动该调度。Batch 也只由数据 API 常驻入口按 `jdb.enabled` 托管，默认关闭；主策略不导入，有限 CLI 强制不启动。保留原 SQLite、Job ID、Quartz 暂停状态和恢复协议。

历史评分按业务生效区间和真实可用时间选择名称、行业与市场状态；没有原件不得用当前资料填历史。正式因子凭证独立于旧 partial 回执，须同时核验来源批准、完整键矩阵和实际值。L2 schema 4 在归档核验及 SQLite 引用提交后才清理旧文件，原始接收日志继续保留。

范围与兼容性见[本轮设计决定](decisions/2026-10-17-来源认证与L2归档.md)。

有限市场发布的发送布局须冻结在请求及 prepared 中；改变发送容量不放宽完整键值、WAL 或原物理目标验证。自定义布局使用版本 2 请求，旧请求按其原预算恢复，不能受当前配置影响。全市场日线的较大发送页仍分段回读，其他入口维持原默认预算。

同一挂牌进程可在原队列锁内预取下一批原文，来源线程只推进 `PLANNED` 到 `FETCHED` 或保留来源拒收，网络调用不占用 SQLite 写事务。消费线程仅发布已冻结响应，仍串行持有原正式发布锁并完成全字段与 WAL 验收；预取不能重发、解锁或改写已发布和待复核任务。磁盘缓存有明确上限，异常及退出必须收拢线程；原队列状态和任务身份保持不变。

年度组可在本组生命周期内复用同一冻结原文的私有解析结构，按纽约日期和完整后续拆股投影；缓存不能包含已发送或实库回读的行对象。每次投影仍生成独立行，原 ZIP 摘要、完整来源计数、原运行字段及 WAL 和物理对象验证继续执行，缓存不能替代任何检查点证据。

美股日线预取对尚未绑定冻结原文的 I/O 错误和 HTTP 5xx 做有界重试；尝试历史、退避时刻与原任务状态在同一 SQLite 事务中保存，重启不重置次数。默认最多三次，每次仍走原持久请求预算；429 和配额等待不消耗这项错误重试次数。等待重试不能被判成来源范围完成，也不能阻塞其他可下载证券。已有原文的校验失败、历史失败任务、范围复核和正式未决状态不自动重置。

更多美股日线来源可按年分段发布，完整原文、连续窗口、行数与发送页必须一起冻结。父来源组只在全部年度原运行再次通过完整回读、物理对象和 WAL 核对后推进；单段成功不能当作证券历史完成。只有已提交的未发送窗口可自动继续，未决段继续阻止重发；空年份需由完整来源重算证明，不补造行情。旧格式、原任务身份及正式运行十万行上限不变。

证券代码不是跨发行人的历史身份。当前官方类别与历史 Stock 标签冲突时，未发布任务保留窗口待复核；当前 ETF 行情不能替代旧普通股票历史。只读覆盖报告区分原目录行、当前类别及窗口重叠，不删除历史候选，也不改写已发送或已验收的证据。

复用市场代码的历史证券可按供应商实际支持的永久代码取得价格，仍写入原日线表，以永久请求代码作为独立 `symbol`，不占用当前发行人的价格键。`us_security_identifiers` 单独记录永久代码、原市场代码、价格键、原目录行和已验收价格运行；导入前必须验证原搜索、完整原文投影、原成功状态、原物理表及全部价格字段。映射只是已核对来源窗口，不是完整上市退市登记，不自动合并或改写其他证券。

永久映射的数据定义版本 2 允许原搜索明确为空的 FIGI 保持 null；永久代码、名称、原目录窗口及成功价格运行仍须完整核对，缺字段和文本 `"null"` 不能替代 JSON null。版本 1 清单继续按原 FIGI 必填规则读取，版本 2 才可提交明确空值；原表、十八列、业务键及旧映射保持不变。

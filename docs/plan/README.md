## 先改这五项

### 1. P1：评分输入可能漏证券

这里的“来源”就是主策略评分要用的数据表和视图：

| 输入 | 从哪里读 |
| --- | --- |
| 股票行情、估值和换手率 | `mv_backtest_daily`、`daily_basic` |
| L2 日特征 | `l2_daily_features` |
| ETF 行情、因子和披露持仓 | `etf_daily`、`etf_factor`、`etf_portfolio` |
| 股票和 ETF 基础资料 | `stock_detail_info`、`etf_basic` |
| 市场情绪、市场状态、交易日历 | `market_sentiment_daily`、`regime_features_monitor_daily`、`exchange_calendar` |

例如某天应有 1,000 只股票，实际只读到 900 只。现在 `requireGrid()` 能确认“这天有数据”，却不能单独证明“应有的股票都到了”；随后仍标记 `sourceComplete=true`。漏掉的股票可能影响排名。这是检查缺口，尚未证明生产数据已经漏了。

- 改法：先确定每种输入每天应有哪些证券，再和实际数据核对，并绑定采集任务的核验记录。名单要考虑上市、退市、停牌和来源范围；L2 等稀疏输入不能要求每天覆盖全市场。
- 验收：删掉一个应有证券、保留当天其他行，必须阻止完整发布；合法稀疏输入仍能通过。直接调用评分 CLI 也要执行同样检查。
- 位置：`QuestDbStrategyInputs.java:71、93、137`、`MainStrategyDataService.prepareScores()`。

### 2. P1：恢复路径判断在 macOS 上有误拦截

`MarginZrzStaging.requireEvidenceFile()` 将根目录转成真实路径，却先拿未解析的文件路径比较。macOS 的 `/var` 与 `/private/var` 指向同一位置，也可能被当成越界。本次多项恢复测试实际报了这类错误。

- 改法：统一使用 `FileEvidenceStore.owned()` 一类的路径校验，同时比较普通路径和真实路径，保留越界及符号链接限制。
- 验收：正常 macOS 临时目录能恢复；文件指向目录外、替换链接、超出大小限制时仍被拒绝。检查其他复制了同类判断的恢复入口。
- 位置：`MarginZrzStaging.java:175`，以及 `MarginAllStaging`、`IndexMonthlyStaging` 等同类实现。

### 3. P1：默认验证不能可靠兜底

`architectureTest` 实际为 `NO-SOURCE`，没有执行测试；扫描配置也只列了 core、data、batch。隔离副本的 `data-app` 离线测试有 160 项失败，既有缺历史文件，也有契约断言和恢复流程失败。

- 改法：恢复架构测试，把迁移后的全部模块纳入检查；无测试时直接失败。逐类排查离线失败，区分代码问题、过期断言和缺样本。
- 样本：必要的小样本放测试资源；依赖原始历史资料的验收单独执行，缺资料明确报缺失。不要靠补造结果或跳过失败变绿。
- 验收：干净检出后，一条命令能跑通离线检查；故意加一条跨层依赖能被抓到。补一个跨平台入口，现有 `run_offline_tests.ps1` 仍只覆盖旧三模块并依赖 Windows。
- 位置：`build.gradle:50、153`、`tools/run_offline_tests.ps1`。

### 4. P1：五条财务源还没完成增量接管

`cashflow`、`income`、`express`、`forecast`、`fina_indicator` 仍有接管缺口。`FinancialGrowthRepairJob` 只是冻结响应的局部修复，还明确保留 `sourceComplete=false`。依赖这些表的财务因子不能据此证明数据持续更新。

- 验收：每条源都验证新增、同季度补披露、历史更正、中断重试。缺完整来源时不推进检查点。
- 位置：`financial/application/FinancialGrowthRepairJob.java`；现有限制见[维护说明](../questdb-maintenance.md#五条财务增量还没接管)。

### 5. P1：重试没有完全使用冻结日期

**A 股判断“今天”、交易日和开收盘，用上海时区 `Asia/Shanghai`，也就是 UTC+8。** 美股用纽约时区，自动处理夏令时；BTC 默认 UTC。真实事件时间统一存 UTC，交易日期用 `LocalDate`，不要给数据库里的时间整体加 8 小时。

这里的问题是跨日重试。例如周五的任务失败，周六重试，仍应完成原来的周五任务。`MainStrategyDailyPipeline` 虽然保存了 `sourceLogicalDate`，部分来源规划却仍重新取上海“今天”，可能改变请求的日期判断或身份。时区正确，也要保留原任务日期。

- 改法：来源规划统一使用计划里的日期；业务时间通过注入的 `Clock` 获取。实际审计时间继续记录真实时间。
- 验收：同一任务跨上海零点、周末和节假日重试，日期、范围、请求身份保持一致；需要换输入时显式创建修订。
- 位置：`MainStrategyDailyPipeline.java:60、225、240`。

## 随后处理

### 6. P2：实时 L2 需要全天负载和归档验收

接收回调同步写 SQLite，每条报文开启连接并提交；最多 200 条形成一批，每批写四个 Parquet，再同步、回读和验摘要。两边都有容量上限，历史不会自动归档。正确性测试不能证明高峰吞吐或长期容量够用。

建议沿用当前 SQLite + Parquet，按下面顺序优化：

1. **复用连接**：SQLite 由固定写入线程维护连接和预编译语句，减少每条报文开关连接。原始记录、批次和检查点的写入统一排队。
2. **原始数据先落盘**：提交成功才计为“已保存”，解析和 Parquet 写入在后面处理。内存队列要有上限，不能当成持久化记录；队列满或磁盘不足要明确报错。
3. **再评估批量提交**：可以把多条原始报文放进一次事务，但尚未提交的报文会增加崩溃丢失窗口。先保留逐条持久化要求，压测后再确定是否调整；不直接降低现有同步级别。
4. **合并归档小文件**：交易日封存后，按日期、数据集合并 Parquet，减少读取大量小文件。先保留现有 200 条批次和恢复引用；新归档核验并切换引用后，才能清理旧文件。文件和行组大小由本机压测决定。
5. **限制容量并验证恢复**：SQLite 与 Parquet 成对备份，定期检查 WAL 大小、待处理数量、磁盘余量和断线缺口。

SQLite 同一时刻只有一个写入方，`FULL` 模式每次事务提交都会同步 WAL；这也是优先复用连接、控制事务次数的依据。见 [SQLite WAL](https://www.sqlite.org/wal.html)。Parquet 行组大小会影响缓存和 I/O，不能直接照搬面向 HDFS 的大行组参数，见 [Parquet 配置](https://parquet.apache.org/docs/file-format/configurations/)。连接复用已实施，其余按上述顺序继续验证。

- 验收：16 标的、48 topic 全天负载下，积压不持续增长；记录落盘延迟、每日空间和重启耗时，并验证强杀后已提交报文不丢、不重复累计。
- 位置：`RawJournal.append()`、`ParquetBatchStore.freeze()`、`AliyunL2MqttCollector.messageArrived()`。

### 7. P2：两套采集链路和模块边界还要收拢

市场目录和通用引擎已拆分，主策略也已移除对应用入口的生产依赖。两套既有同步协议仍分别维护，这项后续工作不等于尚未完成市场目录调整。

data-app 与 Batch 分别维护来源任务、目标和账本。Batch 的 `DataReadiness` 绑定 `jdb_test_*` 快照，默认后续阶段还有未连接的生产器；因子池证据也明确不支持来源完整认证。主策略还通过应用模块及额外 classpath 组合业务。迁移目录本身不能补齐这些能力。

- 验收：正式盘后来源→因子→策略输入完整跑通；故意缺一个上游证书必须阻断。新模块的启动、打包、架构检查一起验证。
- 位置：`DataReadiness.java:61`、`RuntimeConfiguration.stageExecutor()`、`FactorPoolEvidence.java:26`、`market-cn/main-strategy-runtime/build.gradle`。

### 8. P2：历史评分还缺完整的时点数据

评分读取当前 `stock_detail_info` 的名称、行业，再用于历史日期；名称含 ST 会影响筛选。市场状态也只有最新修订视角。来源摘要能固定本次输入，不能证明历史当天已经知道这些值。

- 改法：为会影响历史评分的字段保留可用时间和历史版本；缺历史证据的区间明确限制用途。
- 验收：用更名、ST 变化、行业调整、事后修订样本，确认未来信息不会进入过去的评分。
- 位置：`QuestDbStrategyInputs.java:56`、`L2StockScoreProducer.produce()`；见[主策略说明](../main-strategy-java-data.md)。

### 9. P2：私密配置仍跟代码一起分发

根 `config/application.yml` 含非空来源 token 和管理 API token，构建会复制到各发行包。保存了仓库或发行包，也就保存了这些凭据。

- 改法：公开默认值与私密本地覆盖分开，仍保留本机开箱可用的配置；文档只写配置方式，不抄真实值。
- 验收：仓库和通用发行包不含私密值，本机各进程仍能正确加载配置；缺管理凭据时拒绝开放管理接口。已有凭据是否需要更换另行处理，本次未改。

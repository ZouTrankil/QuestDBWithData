## U1：补齐月包延迟和跨月停跑

1. 每轮冻结 UTC 截止日。按原队列、原运行与实际验收范围计算缺口，不只看最大日期；失败和未决范围不能当作可重建任务。
2. 月包未发布时，有日包能力的数据集补已确认未覆盖日期。404 记录待发布或待核实，不当合法空范围；已验收日包不重复写。
3. 资金费率扫描未覆盖月份，每次 API 请求仍限制同一个月。前月缺口不能因当前月已成功而被跳过。达到条数上限、空响应或缺证时保留未完成，不猜八小时频率。
4. 月包发布后核对日包/API 重叠。相同业务值可接替来源，未知间隔可按已有规则补齐；价格、费率或已有间隔冲突进入显式修订，保留原值和原证据。
5. 使用原队列、请求预算和锁；不能另开下载工程或复制账本。首次补缺仍须正式完整键值、WAL 和原物理目标验收。

验收用例：月末正常更新、月初月包 404、跨月停跑三天、前月资金费率未补完、月包随后出现、月包与日包冲突、相同截止日重复运行、已有未决范围。分别证明缺口被记录或补齐、已验收键不重复发布、未决锁不被解除。

- `revision-review.sqlite3` 保存原报告摘要及待办。发布和当前版本严格读取共同检查；显式历史批次仍可读并返回待办。普通 ZIP 修订只认相同任务、原运行、新 ZIP 及原物理目标的 Java 成功证明；跨来源冲突继续显式复核，不用普通修订结果冒认。记录待修订范围及受影响消费者；原值仍可保留为固定历史版本，但当前用途是否可用由质量规则说明。

## U3：恢复与备份矩阵

已补冻结 API 原文重算与队列收拢、修订恢复状态收拢、一致性备份及隔离核对。底层部分发送补缺仍限定首切片且总量不超过一万行；原值冲突和超出能力的故障保留原锁。下面是实际支持边界，不承诺任意故障自动恢复。

| 故障 | 必须保留 | 处理与验收 |
| --- | --- | --- |
| 来源下载失败、ZIP 截断或校验错误 | 失败原因、预算、已核验原件 | 仅重试未发送来源；损坏临时文件不登记成功 |
| 原文已冻结、尚未提交写入意图 | 原文、摘要、原任务 | 复用原文；先证明没有发布副作用 |
| 已登记意图、部分发送或状态不明 | prepared、原运行、物理目标、锁 | 显式原运行核对；仅在已有恢复协议允许时补确认缺失的键 |
| 全部发送、回读或队列更新中断 | 完整发送证据、账本、原队列 | 核对全部键值、WAL、稳定对象后补齐原状态，不创建新发布 |
| 同键修订中断 | 新旧值、修订意图、原目标和锁 | 按原修订恢复；不能换表或重建请求 |
| 研究批次发布中断 | 旧指针、已发布版本、候选文件 | 按任务 10 保留旧批次，不影响正式写入 |

备份包含原 ZIP/CHECKSUM、API 原响应、SQLite 一致性备份、prepared、回执和研究清单引用的文件。停止 writer 或采用明确的一致性备份方式，不能直接复制活动 SQLite 主文件遗漏 WAL。隔离位置验证恢复引用和摘要；不得让恢复副本连接正式库启动第二个 writer。

每个用例交付触发点、原状态、处理命令、恢复结果及不支持范围。未决不自动重发或解锁，不承诺所有写入都能回滚。

# 时间字段与主策略数据标准统一

依据：[105 个对象逐表核查](../../audits/2026-10-20-cn-time-fields.md)、[字段明细](../../audits/2026-10-20-cn-time-fields-columns.csv)、[主策略数据链路](../../main-strategy-java-data.md)。核对日期：2026-10-20。

## 要解决什么问题

CN 登记的 105 个对象中，同一交易日有 `trade_date`、`timestamp`、`ts` 等名字；相同名字也可能表示不同含义。例如 ETF 日线的 `timestamp` 是交易日，ETF 基础资料的同名字段却是固定 `1970-01-01` 的技术占位。只按名称批量替换，会把日期、分钟时刻和技术字段混在一起。

已有两类具体差异需要处理：`stk_shock`、`stk_high_shock` 的来源输出字段虽然叫 `trade_date`，说明却是公告日期；`index_daily_market` 的实库指定时间列已是 `trade_date`，Java 契约仍映射到 `timestamp`。

逐表核查覆盖 101 个表、4 个原生 MV，共 2321 列，整理了 205 个日期、时刻、周期及相关说明字段。结论是 6 个对象可统一交易日名称，43 个保留现有 `trade_date`，51 个保留其他时间语义，2 个需纠偏，3 个待核。核查使用结构、现有契约和每对象最多 2 行样本，不是全量历史值验收。

主策略也没有全部使用统一字段。读取器仍分别处理股票的 `trade_date/ts_code`、L2 的 `ts/symbol`、ETF 日线的 `timestamp/ts_code`；覆盖清单、历史时点输入和市场输入包还依赖这些名字。相同的 `amount` 在行情中是成交额，在 ETF 持仓中却是持股数量。只改数据库列或目录说明，无法解决整条链路的语义差异。

## 怎样算解决

105 个对象的时间字段都有明确的数据元、类型、编码和来源映射；相同业务含义使用同一逻辑名称，不同含义不因名字相似而合并。6 个已确认交易日别名完成契约、读写和物理结构的统一，2 个公告日期完成语义纠偏，实库与 Java 的结构差异有对应修复。

旧请求、来源字段、业务键含义和原始证据仍可解释；新请求使用明确版本的映射。相关消费者、MV 和恢复流程通过验证后才算迁移完成。只改字典或 Java 字段，不能宣称实库已经统一；待核项没有证据时保留原名并列出缺口。

涉及字段的生产代码、生成模板、测试、SQL、API、Parquet/JSON schema、覆盖清单和消费者都要实际接入标准。主策略从来源读取、历史时点筛选、评分到输入包和正式计划读取逐段验收，不允许数据库改完而运行代码继续依赖旧名字。兼容旧协议的字段必须有明确版本和映射，不能把兼容别名误当作已统一的物理字段。

## 分析与结论

需要改，按“标准数据元、逻辑字段、物理字段映射”分阶段处理。先统一业务语义，再迁移已确认的物理别名；不能把全部时间列改成 `trade_date`，也不能只保留一套建议名而没有实际读写接入。

标准数据元指业务概念及其约束；字段映射记录来源名、逻辑名、存储名之间的关系。现有 `DatasetDefinition.Column` 已有 `sourceName`、`logicalName`、`storageName` 和时间契约，应沿用并补齐，不另建一份只给页面看的独立字典。生成模型的来源说明继续由维护中的资源生成。

范围包括 CN 登记对象的时间命名，以及主策略相关数据的标识、日期、数值单位、空值和发布协议。`ts_code` 是标的代码，不改成 `trade_date`，但它与 `symbol` 的角色和映射也要在主策略链路统一。主策略用到的 `exchange_calendar` 不在这 105 个登记对象中，也要纳入检查；不能把原核查清单当作主策略的完整依赖图。

不修改评分算法、训练权重和交易规则，不补造来源，也不纠正未经原始证据核验的历史时区值。字段标准化可能改变 schema、序列化结果和摘要，必须显式升级版本，不能靠保留旧版本号隐藏变化。

## 修改范围

### 明确统一为交易日

| 对象 | 当前物理字段 | 目标逻辑及物理字段 | 必须保留 |
| --- | --- | --- | --- |
| `etf_adj` | `timestamp` | `trade_date` | 原日期编码、分区与完整去重键含义 |
| `etf_daily` | `timestamp` | `trade_date` | `TIMESTAMP_NS` 精度及行情值 |
| `etf_share` | `timestamp` | `trade_date` | 份额所属交易日与独立的 `update_time` |
| `stk_st_daily` | `timestamp` | `trade_date` | 仅按 SSE 开市日展开的现行规则 |
| `stk_suspend` | `timestamp` | `trade_date` | `suspend_d` 交易日语义，不扩写成全天停牌 |
| `l2_daily_features` | `ts` | `trade_date` | 午夜日期载体与原 `(ts,symbol)` 键的业务含义 |

### 单独修复和规范

- `index_daily_market`：先核对正式读写路径及旧请求，修复 Java 契约与实库列名不一致；不为匹配旧代码把实库改回 `timestamp`。
- `stk_shock`、`stk_high_shock`：逻辑名统一为 `announcement_date`，保留来源字段 `trade_date` 的显式映射。物理改名纳入单独迁移批次，不先把它们认证为交易日。
- `shibor.timestamp`、`hibor.timestamp`、`shibor_lpr.date`：逻辑名统一为 `observation_date`，明确各自利率日期规则；物理改名在交易日批次完成后单独处理。
- `rmb_index_daily`、`dc_index`、`regime_stock_return_distribution_daily.as_of`：补原来源或生产规则。只有证明日期角色相同，才纳入改名清单；午夜样本和表名不是充分依据。

其他 43 个已有 `trade_date` 的对象逐项核对映射、格式和消费者，保留符合语义的名称。51 个其他语义对象按核查清单补齐字典；清单中的建议名先核对来源角色，不批量扩展为物理改名任务。

### 保留区别的时间角色

| 含义 | 统一规则 |
| --- | --- |
| 交易日 | `trade_date`，业务层为 `LocalDate`，按所属市场会话确定 |
| 利率观测日 | `observation_date`，不套用 A 股交易日历 |
| 公告日、报告期末 | 分别使用 `announcement_date`、`report_period_end_date` 等明确角色名 |
| 月份、季度 | 保留周期语义，不转换成虚构交易日 |
| 分钟、事件、接收和计算时间 | 分开命名；真实时刻用 UTC `Instant`，保留精度和来源时区规则 |
| 估值、分析、评估及生效边界 | 保留各自角色，不能默认等于交易日 |
| 技术占位及日期载体 | 明确标注技术用途，不冒充事件或采集时刻 |

`etf_basic.timestamp`、`fut_basic.timestamp` 继续按现有技术占位规则解释。`l2_dataset_manifest.trade_date_ts` 是 `trade_date` 的分区载体且进入去重键，不能直接改成同名列或删除。`update_time` 不自动等于 `ingested_at` 或 `available_at`。

## 主策略数据专项

### 已核对的输入和差异

本次补查 `QuestDbStrategyInputs.TABLES` 登记的 12 个实库对象，每个最多读取 2 行相关字段；同时检查了读取、评分装配、覆盖清单、历史时点和发布代码。结论是字段尚未全部标准化，不代表已经发现全部历史数据错误。本次没有回读实际发布的评分 Parquet、市场输入包和正式计划 SQLite，实施时必须补查这些产物的实际 schema 与值。下表中的差异要进入实施清单。

| 对象或链路 | 当前字段及情况 | 计划处理 |
| --- | --- | --- |
| `mv_backtest_daily`、`daily`、`daily_basic` | 主键使用 `trade_date/ts_code`；行情与每日指标含不同单位的量、额、市值 | 保留交易日语义，统一标的逻辑键；逐字段登记单位、复权口径和稀疏规则 |
| `l2_daily_features` | 使用 `ts/symbol`；样本 `symbol` 为 `000001.SZ` 这类完整代码 | 日期统一为 `trade_date`；同一标的映射到统一逻辑键，同步市场关联和完整性检查 |
| `etf_daily`、`etf_factor` | 日期分别是 `timestamp`、`trade_date`；涨跌幅分别叫 `pct_chg`、`pct_change` | 日期统一；涨跌幅核对单位与未复权/昨收口径后映射，不能只凭相近样本合并 |
| `stock_detail_info` | 样本 `ts_code=000001.SZ`，但 `symbol=000001`；`delist_date` 可为字符串 `None` | 完整代码与本地代码分开；按契约解析空值，不能把无后缀代码直接当跨市场身份 |
| `etf_basic` | `ts_code` 为完整代码，`timestamp` 固定为 epoch | 按静态参考数据读取，技术占位不参与交易日期或可用时间推断 |
| `etf_portfolio` | `ts_code` 是 ETF，`symbol` 是持仓成分；`ann_date/end_date` 是公告和报告截止日期 | 明确 `etf_code/constituent_code` 等角色映射，保留公告可见性、报告期及完整组合键 |
| `market_sentiment_daily`、`regime_features_monitor_daily` | 已有 `trade_date`，另有 `updated_at`；历史记录可在多年后更新 | 交易日与计算/修订时刻分开；历史可用性继续由独立时点证据判断 |
| `exchange_calendar` | `cal_date` 包含日历日期，`is_open` 标识开市；样本 `pretrade_date` 既有 `YYYYMMDD` 也有 `None` | 保留日历日期角色，不整体改成交易日；统一上一交易日的解析和合法空值规则 |
| 评分面板与市场输入包 | 评分面板使用 `trade_date/ts_code`，`etf_market` 组件仍发布 `timestamp/ts_code` | 新版日频市场数据统一日期和标的逻辑字段；同步 schema、元数据声明、读取 API 和消费者 |
| 正式周计划和历史证据 | 有 `symbol`、`signal_date`、`execution_date`、`valuation_date`、`availableAt` 等协议字段 | 区分标的、信号、执行、估值与真实可用时刻；保留旧协议适配，不把不同日期合并 |

直接输入之外，还要沿日批阶段和 MV SQL 找齐 `stk_factor`、`stk_limit`、`stk_suspend`、`stk_st_daily`、`etf_adj`、`etf_share`、L2 清单及情绪/市场状态的上游。补数计划、来源 owner 和覆盖凭证都要跟随映射调整，不能只改读取器列出的 12 个对象。

### 字段存在性和评分可选列

补查这 105 个对象中有来源 JSON 合同的 39 个对象，合同登记的目标列在实库均存在。这只验证列名存在，不证明类型、每行非空、来源覆盖或数值已经全部正确，也不覆盖其余对象的全部业务字段。

主策略 `L2_SCORE_COLUMNS` 的候选读取列中，实库缺少下面 9 列：`q2_accumulation_ratio`、`active_buy_ratio`、`q4_distribution`、`q4_distribution_ratio`、`active_sell_ratio`、`large_active_sell_amount`、`daily_amount`、`amount`、`turnover_rate`。当前读取器只投影存在的候选列，明确要求的 8 个最低必需列均存在；评分器会从行情派生部分字段，其余部分允许缺失参与现有空值规则。因此不能把这 9 列全部判成漏采，也不能自动加列、补零或把其他同名值接进来。

实施时为每个评分输入登记“源表必需、合法可选、行情关联、公式派生、模型要求”的分类，以及来源、公式、单位、缺失行为和批准方案版本。对照真实训练文件、冻结输入和独立参考核验可选列缺失对分数、排名及候选的影响。现有代码允许缺列，不等于当前批准方案接受任意缺失；最低必需列检查也不等于完整模型输入验收。

### 主策略字段标准

- 新版主策略日频市场输入使用 `trade_date` 表示交易日，使用 `instrument_code` 表示同一标的的完整代码；Java 业务字段使用对应的 `tradeDate/instrumentCode`。来源的 `ts_code`、L2 的 `symbol` 通过显式 mapper 转换。代码命名空间、交易所后缀和北交所历史别名规则一并保留，不把代码字符串当作永久标的 ID。
- 一行包含多个标的角色时，使用 `etf_code`、`constituent_code` 等明确角色，不把持仓两侧压成一个 `instrument_code`。现有正式计划 `symbol` 和旧评分 `ts_code` 属于版本化协议；升级时提供明确适配，不能改写历史计划或旧产物。
- 公告日、报告期末、日历日、信号日、执行日和估值日分别建数据元；日期统一对外编码，业务层使用日期类型。`available_at` 表示真实可用时刻，旧协议 `availableAt` 保留版本映射，不能用 `updated_at` 或当前导出时间补造。
- 数值字典必须写清单位、币种、百分比还是小数、价格复权和分母口径。已确认：行情 `amount` 为千元、`vol` 为手，`daily_basic.total_mv` 为万元；ETF 持仓 `amount` 为股数、`mkv` 为元。同名字段不能直接合并。持仓数量等使用明确逻辑名称，如 `holding_quantity`、`holding_market_value`；货币和量纲在契约中必填。
- `pct_chg/pct_change`、`turnover_rate`、`stk_mkv_ratio` 等逐项确定比例尺度和分母；同语义字段才能统一。标准化涉及缩放时必须显式转换，并同步阈值与模型输入适配，不能因为名字统一就直接改变评分使用的数值。
- `price/open_price/raw_close`、`close` 和各类 `_bfq`、前后复权价格逐项写清用途及调整版本。算法、特征名和批准的训练文件之间已有绑定时，在模型边界提供版本化适配；不能直接重命名训练列后继续沿用旧 schema 和批准摘要。
- 空值、零、NaN、空串、`None` 和“缺少整行”分别定义。沿用已批准的停牌、ST、L2 稀疏范围及历史名称/行业规则；标准化不扩大证券范围，不填造报价或停牌标志。
- 字段“存在”“有值”“能计算”“符合批准模型”分别验收。把上述 9 个 L2 候选缺列纳入字段矩阵，不为追求列名齐全而改变原始数据或评分缺失规则。

## 执行与验收

1. **复核基线与依赖。** 执行前重新读取 105 个对象及主策略额外依赖的结构，记录数据库及物理对象身份、指定列、精度、分区、WAL、去重键、MV SQL、写入方和消费者。将每个字段归为改名、保留或待核；找齐 Java、查询 API、生成器、Parquet 导入及 Python 只读消费者。补充主策略输入到评分、覆盖、市场输入包和正式计划的字段矩阵及逐文件修改清单；保留共享工作区已有修改。
2. **统一契约和字典。** 先修复 `index_daily_market` 的映射差异，再为交易日、公告日、利率观测日及主策略标识和数值字段建立明确映射。字典记录定义、来源名、逻辑名、物理名、格式、精度、日期角色、时区或日历、单位、币种、复权口径、比例尺度、空值及键角色；目录 API 和导出复用该定义。真实日期与 UTC 零点日期标记分开，不整体加八小时。
3. **准备并演练迁移。** 按当前服务端实际能力选择显式迁移方式，在隔离目标验证指定列、类型和依赖行为，不预设普通列重命名就能迁移指定时间列。逐批列出原对象、目标结构、步骤、失败状态和恢复操作；如需新物理对象，明确记录身份变化、账本绑定与旧对象保留方式。已有 Flyway 脚本不改，外部归属表不擅自并入示例迁移链。

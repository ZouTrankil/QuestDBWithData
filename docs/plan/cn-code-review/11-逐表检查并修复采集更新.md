### 先让已接通的表产生正式结果

[最新实库检查](../../audits/2026-10-21-cn-connected-table-freshness.md)确认 13 张落后于已经拿到的来源。先从 `cn_cpi` 开始，再按 `cn_ppi → cn_pmi → cn_m → sf_month → cn_gdp → shibor → hibor → cyq_perf` 推进。宏观按统计期、利率按实际观测日；每次重新确定来源已发布上限，不能把旧探测日期当作最新上限。

### 其余表怎么收尾

- 25 张已接通表：以[逐表状态](../../operations/cn-time-migration/逐表状态.csv)和[新鲜度检查](../../audits/2026-10-21-cn-connected-table-freshness.md)为准。六张日期布局迁移与依赖 MV、消费者一起切换；财务五表继续原预算与队列；LPR 没有新来源时保留缺口；L2 必须有真实输入及恢复材料。不能重做一遍 owner 代替正式补数。
- `stock_minute_bars`、`margin_trading`、`index`：找到原文件、范围和导入记录，确认继续更新还是仅保留历史；缺文件时单列跳过。
- `l2_live_normalized_events`：核清历史归属，当前实时链路仍用 SQLite WAL 与类型化 Parquet，不恢复旧 QuestDB writer。
- `margin_zrz`、`moneyflow_dc`、`qmt_1m_bars`：确认停写和依赖、账本、锁、stage/backup 恢复归属后，执行既有退役清理并核验，不能因为代码已删就当数据也已删。

每张正式完成记录必须有：实际目标、明确来源范围与截止日、补数结果、全部键值/WAL 核验、修订与恢复结果、后续更新结果，以及相关 MV／消费者状态。尚未到下一次发布窗口就写“首次范围通过，持续更新待验”，不能提前标完成。小改只跑相关测试，阶段末统一检查架构、边界和受影响发行包。

## 每张表怎么做

1. 查来源、更新频率、负责程序和实际写入表。
2. 看最近一次成功和报错，查清是没开、写错表、等配额，还是来源没有新数据。
3. 复用已有采集程序修好，一次只处理一张表。财务请求太多就分批，配额用完或重启后接着跑。
4. 核对来源范围、证券、全部字段值和 WAL，再检查下一次更新是否正常。最大日期变新不算验收完成。

已发送但结果不确定的任务按原流程恢复，不自动重发或解锁。已有补数记录先核对，避免重复执行。

## 怎么算完成

每张表留下：最新数据日期、上次成功时间、实际原因、修了什么、验证结果。查不到的写“待查”。纯历史数据标明只留历史，不硬加日更。

结果放回现有目录或状态接口，能直接看到哪张没更新、为什么，不另开一个监控项目。

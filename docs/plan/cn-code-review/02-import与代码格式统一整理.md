# 全项目 import 与代码格式统一整理

合并原第 2 项 import 和第 3 项代码格式问题。依据：下文列出的源码及全项目静态候选扫描。核对日期：2026-10-20。

## 要解决什么问题

已确认的可读性问题有两类：已 import 的类型仍在正文重复写完整包名；一个物理行中挤入多个业务或数据库操作。前者让字段和构造器难以浏览，后者让断点难以停在单次参数绑定、状态检查或提交操作上。

`StockCommands` 可直接看到重复限定名；`UsBroadSourceRetry.record()` 可看到参数绑定、执行更新和事务处理压在一行。问题跨多个模块存在，下方统计用于确定整理范围，不表示每个候选都违反规则，也不证明已经造成数据错误。

需要按用户要求统一整理。解决目标是降低全项目阅读、断点和审查成本，不改变采集或恢复结果。

## 怎样算解决

主代码、测试及生成模板使用同一套明确规则；非必要全限定名和密集多语句已逐项整理，合理例外有说明。关键业务操作可以逐行打断点，生成后不会再次输出旧格式。覆盖清单、编译、相关回归和原有接口行为都能核对。

## 分析与结论

需要统一处理，范围扩展到全项目 Java 主代码、测试代码和相关生成模板，不只整理 CN CLI 或某个 US 类。先定统一规则，再按模块执行，避免每个文件换一种排版。

本次对 `platform/`、`markets/` 和根 `src/` 的 2,006 个 Java 文件做了静态候选扫描，去除注释和字面量，并排除括号内的分号。结果如下，三类文件存在重叠，不能相加：

| 检查项 | 候选文件数 | 如何判断 |
| --- | ---: | --- |
| 正文使用全限定类型名 | 831 | 同名冲突等情况可能合理，不能全部替换 |
| 已有 import，正文仍使用同一完整类型名 | 66 | 优先整理，仍需核对名字解析 |
| 同行有多个括号外分号 | 1,104 | 优先展开业务、事务和恢复流程；不把所有紧凑访问器判成错误 |

这是文本扫描，不是 Java 语法解析或编译结论，可能漏掉或误报。当前没有扫描出来就能自动删除的“无用 import 清单”，此项需要 IDE 或语法工具确认。

典型位置：

- [StockCommands](../../../markets/cn/data/src/main/java/com/zoutrankil/data/cli/StockCommands.java)、[IndexCommands](../../../markets/cn/data/src/main/java/com/zoutrankil/data/cli/IndexCommands.java)：已有 import，字段和调用仍重复使用完整包名。
- [StockBasicWriteGroupService](../../../markets/cn/data/src/main/java/com/zoutrankil/data/service/StockBasicWriteGroupService.java)：多种已导入类型在正文重复全限定。
- [UsBroadSourceRetry](../../../markets/us/data-app/src/main/java/com/zoutrankil/market/us/app/UsBroadSourceRetry.java)：参数绑定、判断、提交和回滚压在同一行，不便断点审查。

## 统一整理规则

- 使用明确的 import 和简单类型名；清理无用及重复 import，整理现有通配符 import。确有同名冲突时保留必要限定，不为省包名引入歧义。
- 统一缩进、空格、换行和大括号排版，展开同行多语句、密集条件和 try/catch。事务、写入、核验、取消与恢复流程应能逐步打断点。
- 保持 SQL、JSON、正则、命令、错误消息、配置键、反射字符串及持久化类名的实际值不变；不借格式整理迁包、重命名或修改算法。
- 保持执行顺序、绑定参数位置、事务边界、异常传播和锁生命周期。只有排版变化时，不顺便调整分支或提取新业务抽象。
- 原有中文注释随代码保留。补核心说明或修改注释时用简短中文，不逐行复述语句。
- 生成代码先找维护中的生成器或模板，修复输出格式并核对生成差异；输入或历史快照缺失时明确记录，不手工改生成结果冒充已接管。
- 先检查工作区 diff 并保留已有修改；根 `build/`、日志、归档、第三方代码和历史证据不属于格式整理范围。

当前根构建未发现统一的 Spotless 或 Checkstyle 配置。执行时先确认现有格式工具，选择兼容 JDK 24 的一致规则和可重复的检查方式，再分模块整理；若新增工具，依赖与锁文件一并验证。

## 执行与验收

先完成全项目清单和统一规则，再按公共平台、CN、US、BTC 分批处理主代码和测试。每批检查实际 diff 与编译结果，最终汇总覆盖范围，不能只改典型文件就说全项目完成。

编译和相关离线回归通过后，再检查 `architectureTest`、`verifyModuleBoundaries`、依赖兼容及受影响发行包。全项目整理应执行项目离线检查入口，真实来源与数据库写入验收不因纯格式改动默认启动。关键请求 JSON、身份哈希和 SQL 原值不能因整理变化；用现有相关回归核对，不给每个换行新增测试。

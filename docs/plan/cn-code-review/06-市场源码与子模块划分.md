# 市场源码与子模块划分

依据：[settings.gradle](../../../settings.gradle) 与三个市场的现有构建和源码目录。核对日期：2026-10-20。

## 要解决什么问题

已确认的是模块角色容易混淆：`:markets:cn`、`:markets:us`、`:markets:btc` 一面作为市场父路径容纳子项目，一面本身还是带源码的库。看到市场目录下同时存在 `src`、`data`、`data-app` 时，容易误以为 `src` 没有模块归属，也难以直接看出共享模型应该依赖哪个库。

此外三个根库的职责和依赖不同：CN 有模型、契约、目录及 Jackson 依赖，US 依赖 `engine:source`，BTC 依赖 core。它们不能仅凭目录形状统一视为纯模型库。

当前没有证据表明这种结构已经造成构建失败或跨市场调用。它是结构理解和依赖表达问题，模块迁移成本可能大于改名收益，不属于必须立即修的故障。

## 是否需要改业务代码

先澄清现有模块职责和消费者。只有依赖清单能说明拆分后哪些职责或依赖边界会更清楚，才实施最小迁移；收益不足则保留结构，只补目录说明。不能因为有 `src` 就先创建一个叫 `src` 的子模块。

## 怎样算解决

读者能从结构说明找到共享模型、来源实现和运行入口的归属及依赖方向。若实际拆分，父工程只聚合，源码、资源、SPI、测试和发行包都正确迁移，原任务与数据协议兼容；若不拆分，明确保留原因，不虚报已完成模块改造。

## 分析与结论

当前 `markets/cn/src` 已属于 `:markets:cn` 这个 Gradle 库，不是没有模块归属的散落源码；US、BTC 同理。旁边的 `data`、`source`、`data-app` 是子项目，各有自己的 `src`。

可以改进的是：让市场父工程只聚合，把父工程自己的源码和资源移入语义明确的叶子模块。是否拆分取决于明确的职责和依赖收益，不作为默认必须执行的迁移。

不要直接把新模块叫 `src`。CN 主要放模型、契约及目录资源，可评估 `model` 或 `contracts`；US 还含来源、映射和行情定义，当前依赖 `engine:source`，不能不核对就称为纯模型库。BTC 也要按实际职责划分，三个市场不必机械拆成相同目录。

需迁移源码、资源、SPI 与测试，并更新 Gradle 依赖、生成器路径、架构规则、配置分发和发行包。优先保持 Java 包名、任务类名和数据协议，避免把迁模块变成数据迁移。

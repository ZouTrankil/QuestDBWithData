# 数据目录、说明、标签和导出接口

状态：首期接口已实现。记录及实现日期：2026-10-17。使用方法见[数据目录接口](../data-catalog.md)。

目标：启动 App 后，就能查询当前 QuestDB 有哪些数据、各自是什么、来自哪里，并按市场和多个标签筛选、导出 CSV。把这次人工整理的数据清单变成应用能力。

## 1. 现有基础和本次范围

现有 `GET /api/v1/datasets` 返回 `DatasetRegistry` 已注册的数据集定义。`DatasetDefinition` 已包含字段、业务键、来源和依赖等契约，但注册列表不能代替实库的完整对象清单，也缺少统一的业务说明、多标签和目录 CSV 导出。

以[现有分类 CSV](../../outputs/questdb-classification-20261017/QuestDB数据分类.csv)作为首批说明的整理依据。开发时重新核对实库，不把这份文件里的对象数量、行数和最新日期写死到代码里。

首期提供数据目录 JSON、单个对象说明、标签列表和目录 CSV 导出。目录 CSV 每个表或视图一行。业务表内的明细数据导出另列后续需求，届时明确日期、证券、字段和行数范围。

## 2. 数据目录怎么得到

将两部分合并：**实库元数据 + 代码维护的业务说明**。

- 实库元数据：只读发现普通表、普通视图和原生物化视图，获取字段、时间列、可取得的行数及 MV 刷新信息。按物理对象名去重，不能把同一个 MV 统计两次。
- 业务说明：在 Java 中登记中文名称、用途、市场、来源分类、标签、上游、维护方式和注意事项。已有 `DatasetDefinition` 的字段含义、业务键和依赖优先复用。
- 新发现但未登记说明的对象照常列出，标记 `UNCLASSIFIED`，说明和来源显示“待补充”。不能只靠表名前缀猜测用途。
- 默认列出当前实库存在的全部业务对象，包括暂存对象。代码有登记、实库已删除的对象，只在 `includeMissing=true` 时列出并标记 `MISSING`。
- 目录里可见，不代表已经提供业务数据读取能力；读取能力继续由现有数据集注册和读取守卫决定。

数据库连接失败时返回明确的不可用错误，不能返回一份空清单并称数据库没有数据。暂时取不到的统计值用 `null`，不能填成 `0`。目录请求不执行全表 `COUNT(*)`、刷新 MV、建表或补数据。

## 3. 每个对象提供哪些说明

| 内容 | 字段建议 | 维护方式 |
| --- | --- | --- |
| 物理对象名、对应的数据集 ID | `objectName`、`datasetId` | 实库名称；已注册时关联数据集 |
| 中文名称、内容和用途 | `displayName`、`description` | 代码登记 |
| 市场归属，可有多个 | `markets` | A 股、美股、BTC、共用/跨市场 |
| 业务分组、来源分类 | `businessGroup`、`sourceType` | 采集、衍生、运行生成；未登记为未知 |
| 多个标签 | `tags` | 代码中的标签集合 |
| 来源和上游对象 | `provider`、`upstreamObjects` | 复用已维护契约，补充业务说明 |
| 维护方式、限制和说明依据 | `maintenance`、`notes`、`descriptionBasis` | 代码登记，不由对象名称推断 |
| 对象类型 | `objectKind` | 实查 `TABLE`、`VIEW`、`MATERIALIZED_VIEW` |
| 存在状态、说明完整性 | `presence`、`classificationStatus` | 区分存在、缺失、未分类 |
| 行数、覆盖起止时间、元数据采集时间 | `rowCount`、`minTimestamp`、`maxTimestamp`、`observedAt` | 实库元数据；缺失值保留未知 |
| MV 状态、刷新方式、基表和最近刷新时间 | `materializedView` | 实库 MV 元数据 |
| 字段、类型、含义、时间语义及业务键 | `columns`、`businessKey` | 详情接口提供；缺失的业务含义标记待补充 |
| 是否支持现有业务读取 API | `readSupported` | 由真实注册和能力判断 |

来源分类和对象类型分开。例如，采集来的技术因子仍可属于“采集”；原生 MV 的来源分类为“衍生”。不能把所有带 `factor` 的表都归为运行生成。

最大数据日期、最近刷新时间和行数分别展示，不能直接据此断言“同步正常”或 `DataReady`。例如 `mv_backtest_daily` 的说明须写明基表 `stk_limit` 触发刷新，关联表单独更新不会触发。

## 4. 标签在代码中维护，一个对象可以有多个

定义统一标签字典，包含稳定的标签 ID 和中文显示名。使用 `Set<String>` 或标签枚举保存对象的标签，校验未知标签和重复登记。

标签示例：`CN`（A 股及国内）、`US`（美股）、`BTC`、`SHARED`（共用）、`EQUITY`（股票）、`ETF`、`MACRO`（宏观）、`L2`、`DAILY`（日频）、`BACKTEST`（回测）、`COLLECTED`（采集）、`DERIVED`（衍生）、`GENERATED`（运行生成）。

登记示意，实际条目还包括来源、维护方式和上游等字段：

```java
Set.of(CN, EQUITY, DAILY, BACKTEST, DERIVED)
```

按市场维护各自的说明登记，App 统一组装。标签和业务说明只维护这一份代码定义，不在不同 profile 中复制，也不再手工维护另一份长期 CSV。数据库连接、查询超时等运行参数仍使用根 `config/`。

新增市场或标签时扩展代码登记。支持 BTC 分类不代表当前数据库已经有 BTC 数据；没有对象时如实返回空筛选结果。

## 5. 接口计划

新增独立的数据目录接口，保留现有 `/api/v1/datasets` 的返回契约。

| 接口 | 用途 |
| --- | --- |
| `GET /api/v1/data-catalog` | 分页查看目录，返回目录采集时间、总数和对象说明 |
| `GET /api/v1/data-catalog/tags` | 查询标签 ID、中文名及当前对象数量 |
| `GET /api/v1/data-catalog/objects/{objectName}` | 查看单个对象的说明、字段和 MV 信息 |
| `GET /api/v1/data-catalog/export?format=csv` | 下载满足筛选条件的完整目录 CSV |

列表和导出共享筛选规则：`market`、`sourceType`、`objectKind`、`tag`、`keyword`、`includeMissing`。重复传入多个 `tag` 时要求全部满足，例如 `tag=CN&tag=ETF`。未知枚举或标签返回参数错误。

列表按 `objectName` 固定排序，支持 `page`、`pageSize`；导出包含筛选后的全部目录条目，不受列表页码影响。标签数量统计采用同一目录快照中的当前存在对象。列表、详情和导出复用同一个应用服务，避免维护不同的数据分类逻辑。

接口沿用现有数据 API 的鉴权。数据库调用设置超时，按现有 WebFlux 方式离开事件线程执行。返回 `observedAt`；若后续增加短时元数据缓存，必须标明采集时间和缓存有效期。

## 6. CSV 怎么导出

保留现有清单的列顺序，末尾增加“标签”：

```text
市场分组,业务分组,来源分类,对象名,数据库类型,内容/用途,来源或上游,维护方式,当前行数,对象状态,备注,判断依据,标签
```

UTF-8 编码并带 BOM，使用标准 CSV 引号和转义。标签按 ID 排序后以分号连接，例如 `BACKTEST;CN;DAILY;DERIVED;EQUITY`。多个市场和上游也用分号连接；未知行数留空。

响应使用 `text/csv; charset=UTF-8` 和下载文件名 `questdb-data-catalog-YYYYMMDD-HHmmss.csv`。导出数据直接来自目录服务的一次采集结果；不读取旧 CSV 充当当前实库状态。

接口使用方式：

```sh
# 先按现有方式启动数据 API；API_BASE 指向实际服务地址。
./gradlew webRun

# 在另一终端查看 A 股 ETF 数据。
curl -f -H "Authorization: Bearer ${APP_WEB_API_TOKEN}" \
  "${API_BASE}/api/v1/data-catalog?tag=CN&tag=ETF"

# 导出全部当前数据目录。
curl -f -H "Authorization: Bearer ${APP_WEB_API_TOKEN}" \
  "${API_BASE}/api/v1/data-catalog/export?format=csv" \
  -o questdb-data-catalog.csv
```

服务地址和鉴权值按[配置说明](../configuration.md)设置，文档不填写实际凭据。

## 7. 实现位置和步骤

当前工作区正在迁移模块，落地时以 `settings.gradle` 和实际源码位置为准。按职责拆分：通用目录值对象和端口、QuestDB 元数据适配器、各市场的说明登记、目录应用服务、App 的 HTTP/CSV 入口。市场说明不塞进通用数据库适配器，Controller 只处理请求和响应。

1. 固定目录字段、标签字典和 CSV 列，确定说明与现有 `DatasetDefinition` 的关联方式。
2. 从现有 CSV 整理首批代码登记，逐项核对物理名称、来源、用途和多标签；不导入冻结的行数和日期。
3. 实现实库发现与合并，覆盖未分类对象、缺失对象、统计未知和普通视图/MV 去重。
4. 实现列表、详情、标签接口和筛选，再接入同一服务的 CSV 导出。
5. 补接口说明和调用示例，启动 App 对照当时实库验收。

## 8. 验收标准

- 当前实库对象都能发现；新表未登记说明时显示未分类，不能静默漏掉。
- 一个对象支持多个标签；标签筛选、排序、分页符合接口约定。
- 已删的 `backtest_daily`、`qmt_tick_data` 及旧 `_v1` 名称不出现在默认当前目录中；登记残留仅在查看缺失对象时显示。
- 四个现用原生 MV 显示正确类型及刷新信息；不能因其出现在表元数据中而重复列出或归成普通表。
- 在同一元数据输入下，JSON 列表与 CSV 的对象集合、说明和标签一致；CSV 能正确处理中文、逗号、引号、换行和空值。
- 实库不可用时明确失败，未知统计不显示成零；仅查看目录或导出时不触发数据库写入、刷新和全表扫描。
- 有目录条目但未注册业务读取能力的对象，不能因此绕过现有读取守卫。

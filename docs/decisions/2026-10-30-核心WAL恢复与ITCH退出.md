# 核心 WAL 恢复与 ITCH 退出

本轮依据用户明确要求“修复wal、去掉ITCH”执行。两张核心表已恢复，ITCH 已归档后退出正式库；没有重启数据库、跳过事务、重发行情、改旧 Native 或重置预算。

## WAL 恢复

实查 QuestDB 10.0.1：`us_equity_daily` 为 `5056/4994`，`crypto_ohlcv` 为 `610/602`，HTTP 与 PGWire 一致，无缓冲、未挂起、无错误消息。两张 sequencer 日志均不存在高于 writer 已应用水位的事务。该状态是反向水位异常，不能解释成普通待应用积压；目前没有证据将根因归因到某个外部操作。

先取得原采集和账本五把锁，核对无原写入进程、无 Native 未决和区间锁。隔离表在当前服务验证了 `REBASE WAL`：旧值、微秒、最早日期、乱序插入及业务键去重均通过，随后删除隔离表。

服务原本启用 `cairo.wal.apply.suspended.write.denied=true`，本轮没有修改服务配置。暂停后完整备份 1477 个文件、6842760332 字节，逐文件 SHA-256 对照通过。第一次维护被暂停变化门槛拦住，第二次在备份文件比较拦住，均未进入重建；24 个文件的变化经独立核对只是预分配尾部缩短，留下的字节与原备份前缀完全相同。原失败、备份和续接意图分别保留，没有覆盖或直接重跑失败运行。

显式续接重新持有原锁，连续三次确认暂停及原水位稳定，再分别重建。每张表先等待两个种子事务单独结清，才允许后续新任务，避免当前版本已知的“种子与首笔写入同批导致最早时刻异常”。本轮没有向正式表插入新行情。

完整字段、去重键、分区业务元数据、首尾日期、TTL、`maxUncommittedRows` 和 `o3MaxLag` 保持。1455 个数据及索引文件完成核验：业务数据及字典内容相同，预分配尾部缩短时逐字节核对共同前缀；符号索引只允许前 64 字节控制头变化，索引载荷相同。元数据和 sequencer 因重建发生的控制变化另列，不冒称它们字节不变。

全部旧控制 SQLite／Native 的有类型记录摘要不变。核心 80054 条二十列、币价 370198 条十三列，HTTP／PGWire 全量对照一致，并沿原来源、prepared 摘要与原 Native 再验；分别覆盖 35 份来源／组合来源及 610 份来源。原生 BTC 六表的 WAL 保持原水位。新旧物理身份只记到本次迁移证据，不改写旧成功运行或冻结归属。

`REBASE WAL` 会丢弃未应用事务并改变内部 table ID，所以本次“无待应用事务”和完整旧数据保护是前提，不能用于绕过未决发送。[官方语义](https://questdb.com/docs/query/sql/alter-table-rebase-wal/)与[当前版本种子事务问题](https://github.com/questdb/questdb/issues/7842)分别解释重建边界及等待要求。

## ITCH 退出

退出对象只有 `us_nasdaq_itch_messages` 的 450836 条局部原始订单消息，不是把日线／小时线时间戳截断，也不涉及 A 股 L2 或删除既有美股分钟线。

退役前确认原表 ID 3208、WAL 131/131，无普通视图或原生 MV 依赖。47 个物理文件压缩归档并逐文件 SHA-256 回验；完整十六列另导出，`ts` 转整数纳秒、`observed_at` 转整数微秒，450836 行均与 PGWire 对照相同，原纳秒没有经过 Python `datetime` 截短。

随后 Java 维护入口取得原锁及 ITCH 来源锁，复核当前物理文件、字段、依赖和 WAL，冻结单独退役意图，设置停止标记，暂停并仅删除该精确表。删后确认正式表不存在，核心 WAL、原控制库和 Native 保持。旧压缩前缀、原始 metadata、prepared 和回执继续保留。

根配置 `app.market-data.itch-enabled: false` 默认阻止 `fetch-itch-prefix` 和 `import-itch`，检查发生在存储对象及来源读取之前。未来若明确恢复，须新建恢复计划并处理归档、原停止标记及新物理身份，不自动重用成功运行。

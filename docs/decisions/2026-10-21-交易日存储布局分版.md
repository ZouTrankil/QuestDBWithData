# 交易日存储布局分版

先保留旧布局，再显式接入新布局。`etf_adj` 的旧端口把 `timestamp` 写死在预检、范围、完整键回读和日期盘点中；只改 DDL 会让原任务读写失败。反过来按实库“碰到哪列就用哪列”，又会让冻结请求的版本失去意义。

`CnTradeDateLayout` 只允许已核定的六个对象。v1 保留原来的 `timestamp/ts`，v2 选择 `trade_date`；利率、公告、技术 epoch 和待核对象不能套用。它只选择布局，不转换日期、不加八小时，也不改变类型精度。存储布局 v2 与主策略输入协议 v2 是两件事。

本批只接通 `etf_adj`：

- 契约、隔离 DDL、范围查询、写前预检、完整键/整日回读和类型化读取共用显式布局。
- v2 仍使用 TIMESTAMP 微秒、UTC 午夜日期载体、YEAR/WAL 和原完整业务键；来源 `trade_date`、原始日期及复权因子数值不变。
- 原 `EtfAdjWriteSession` 代表固定 v1；分版会话显式实现 `Versioned`。适配器核对冻结定义与会话版本，版本不符时在日历、来源和物理预检前停止。
- `EtfAdjSyncJobOwner.definition(2)` 生成独立 v2 定义和请求身份。原 `DEFINITION`、兼容构造及公开默认值仍是 v1，不改写已有请求、回执或检查点。

控制服务已接通显式 v2 装配：新计划和新执行使用选定布局；恢复、已完成来源再验证及原日志核对使用原账本的作业版本。配置和组入口的范围见下文；其余五张表端口、Batch 独立来源任务、正式表、MV 和消费者没有迁移。

## 怎么核验

离线回归核对版本不符先失败、原 v1 默认与编码不变、新布局列名、完整键回读、日期精度、WAL 和目标身份检查。新布局遇到旧物理列或新物理身份时，不能借 Sender 自动补列或继续发送。

实库验收使用已有正式表的两行只读样本，先耐久保存期望、DDL 意图、目标身份和 v2 请求，再写唯一的 `java_d015_etf_adj_layout2_*` 表。每次发送后核对完整键值、类型化读取、行数、WAL 与稳定身份；第一次全部通过后才做第二次幂等写入。客户端停止后，只清理本测试创建且身份未变的表。

```sh
APP_LOCAL_CONFIG=file:/绝对路径/config/application-local.yml \
D015_LAYOUT_LIVE_ACCEPTANCE=true \
D015_LAYOUT_EVIDENCE_ROOT=var/etf-adj-layout-acceptance \
./gradlew :markets:cn:data:test --tests '*EtfAdjLayoutLiveAcceptanceTest'
```

默认不运行此实库测试。证据目录存在未完成记录时先停止；写入未决不自动重发或删表。报告只写错误类型，不复制账号和异常中的配置。未尝试 DDL 的失败可以重新运行；已尝试建表的失败需先人工核对原表和原件。

实际两行验收已通过，隔离表已清理，正式表身份与事务版本在验收期间不变。它验证 Java 读写布局，不证明来源完整、全历史、模型批准或正式迁移已完成。结果见[实库原件](../operations/cn-time-migration/ETF复权v2端口实库验收.json)和[代码验证](../operations/cn-time-migration/ETF复权v2端口代码验证.json)。

## 控制服务怎样保留原版本

`EtfAdjJobService` 的显式构造参数只用于新计划。原有 `--resume-from` 分支直接恢复账本，不重新规划今天的范围或检查点；通过账本 `jobVersion` 选择固定的 canonical 定义，再校验原 JSON、请求指纹和目标身份。当前默认换成另一版也不改写原请求。新运行则必须匹配当前显式选择，不能拿旧计划冒充新版新运行。

目标的 `Versioned` 能力按请求版本创建会话和读取范围。旧目标接口仍固定 v1；返回会话的声明版本也要再核对，不能由旧包装器偷偷返回 v2 会话。原物理身份变了就停止，不能因为逻辑表名相同而改绑。

检查点只合并同一版本、同一目标的原完整回执。即使人为使用相同目标身份，v2 也不能拿 v1 回执拼接连续前缀。原 `IN_DOUBT` 状态仍禁止直接恢复；原日志核对仍先确认写入进程停止，并要求原区间锁、原来源和原写后证明，未满足时不写数据、不释放锁。

这些变化用临时 SQLite 和原冻结 JSON 验证，包括两种配置方向的旧版本恢复、缺失原锁及连续区间跨版本混用。没有执行真实恢复、变更生产配置或清理未决记录，范围见[控制服务验证](../operations/cn-time-migration/ETF复权v2控制服务验证.json)。

## 配置与组入口

根 `config/markets/cn.yml` 的 `app.sync.etf-adj-schema-version` 默认 `1`，只接受 `1/2`；标准环境覆盖为 `APP_SYNC_ETF_ADJ_SCHEMA_VERSION`。同一个值装配新作业注册、单表计划服务、目标端口、读取仓库和公共读取绑定。新配置不建表、不迁数据；v2 碰到旧物理列时仍须在发送前拒绝。

`DatasetImplementation.definition(version)` 默认只接受当前版本。只有显式实现的 owner 才能提供历史契约；注册表再次核对数据集、版本、provider、owner、对象名和对象种类。`etf_adj` 显式保留 v1/v2，其他实现没有因此自动开放历史版本。

写入组从 JSON 解析、计划指纹、作业注册到实际 writer 都按成员 `definitionVersion` 选择。旧组在当前配置为 v2 时仍使用原 v1 契约和原指纹；反向也一样。实际会话错版时在预检和发送前停止。原目标身份、完整键值、WAL、区间锁和未决恢复规则不变。

该设置控制数据应用的当前 `data.etf_adj` 注册，不改写 Batch 独立 `source_etf_adj` 任务、已有 Quartz 元数据或冻结组请求；正式调度和迁移须另按原部署验收。其他五个物理日期别名也未因此切换。验证见[入口验证](../operations/cn-time-migration/ETF复权v2配置与组入口验证.json)。

## ETF 日线接入范围

`etf_daily` 的 v2 契约、隔离 DDL、范围、完整键/整日回读和类型化仓库均显式选择 `trade_date`。保留 `TIMESTAMP_NS`、UTC 午夜纳秒载体、YEAR/WAL、去重键含义及原十一列数值和空值；不套用复权表的微秒处理，不自动探测列名或自动补列。

根市场配置新增 `app.sync.etf-daily-schema-version: 1`，环境覆盖为 `APP_SYNC_ETF_DAILY_SCHEMA_VERSION`，只接受 `1/2`。单表新计划、当前作业、目标和公共读取绑定共用它。默认仍 v1；`EtfDailySyncJobOwner.DEFINITION` 及旧构造保留原定义。

恢复、已完成来源再验证、原日志核对和检查点都按原账本版本。恢复核对原 JSON 指纹和目标；新计划不接受与当前配置不同的版本。新会话通过 `EtfDailyWriteSession.Versioned` 声明布局，旧泛型会话仍固定 v1；写入组也核对实际会话。日线原有的来源预算、正式表仅允许有界 BACKFILL/RECONCILE、停机日志、区间锁和不确定写入处理保持不变。

实库验收与离线验证分别记录在[日线验证报告](../operations/cn-time-migration/ETF日线v2验证.json)。它们不证明来源全历史完整、正式调度或模型批准。Batch 独立 `source_etf_daily`、其余四张物理别名、MV 与消费者正式迁移仍待完成。

## ETF 份额接入范围

`etf_share` 原作业是 v3、数据契约是 v1。新布局使用作业 v4、契约 v2；`definition(jobVersion)` 只认已登记的 v3/v4，`forLayout(schemaVersion)` 才按布局选作业。不能把旧作业重新编号为 v1，也不重建未登记的更早作业协议。

根市场配置新增 `app.sync.etf-share-schema-version: 1`，环境覆盖为 `APP_SYNC_ETF_SHARE_SCHEMA_VERSION`，仅支持 `1/2`。当前 owner、计划、目标、类型化仓库和公共读取绑定共用它。写入组的成员版本仍是契约 v1/v2，不是作业 v3/v4。

只把指定日期列从 `timestamp` 换为 `trade_date`，保留 TIMESTAMP 微秒、UTC 午夜日期载体、YEAR/WAL、六列值和原完整业务键。`update_time` 仍为独立 UTC 观察时刻；新来源计划冻结一次 `observedAt`，恢复继续用原值。旧物理样本每行已有不同 `update_time` 时，迁移逐行保留，不能覆盖成统一的新时刻。

检查点按原作业版本筛选全部回执，包括修订值的最新凭证；v3/v4 不能拼接连续前缀或借用修订值凭证。普通恢复仍核对原 JSON 指纹和物理身份，未决状态不允许自动重发或解锁。既有 366 日、SH/SZ/O 三市场分片、5997 行日期上限、预算及来源原文核验均保留。

生产仓库、目标和 writer 继续只接受 D016 隔离命名空间，没有借分版开放正式表。实库演练只读正式表两行，按显式 prepared 写入组冻结各行原值，再验证独立 v2 表；它不冒充按统一观察时刻生成的新来源同步作业。范围见[份额验证](../operations/cn-time-migration/ETF份额v2验证.json)。Batch 独立来源、正式接管、调度、其余三表、MV 与消费者迁移仍待完成。

## ST 存储分版

`stk_st_daily` 不只是日线追加。名称变更修订会撤销旧正记录，正式执行还要核对窗口外数据、stage、backup 和发布状态。本批先接通显式 v2 存储，不增加生产配置开关，也不登记新版来源作业。

契约 v2 的逻辑键和物理日期列均为 `trade_date`，保留 TIMESTAMP 微秒、UTC 午夜日期载体、YEAR/WAL、完整证券代码和正 `is_st=1` 行。来源仍按原 SSE 开市日展开；没有改名称区间算法，不补 `is_st=0`。

`StockStDailyMapper` 和 writer 显式选择编码；原 `CODEC` 仍是 v1 的 `timestamp` 字节，新 v2 生成独立 `trade_date` 字节及摘要。旧源码证据、模型字段、默认构造和静态 codec 不重写。类型化读取、完整键/整日/日期盘点和存储快照共用所选布局；快照仍按完整顺序、全部值、稳定物理身份及 WAL 核验。

旧来源作业和写入组若收到 v2 会话会先拒绝，不能把新版编码塞进旧回执。当前注册、CLI/调度、staging、发布、检查点、备份和恢复还没有接入 v2；这一批不能宣称 ST 同步入口或正式迁移完成。

真实两行隔离表验证 writer 的两轮写入、类型化读取、完整快照、窗口/窗口外结果及独立字面量生成的摘要，范围见[ST 存储验证](../operations/cn-time-migration/ST日频v2存储验证.json)。它不执行名称变更来源、不产生生产检查点，也不验证发布切换或恢复。正式表和已有 stage/backup 保持原状。

## ST 显式发布与恢复分版

ST 的 v2 staging、两次 rename 发布及原日志恢复已接入明确布局。`StockStDailyTarget.forFrozenVersion` 只从原冻结请求选择作用域，核对版本和表名；原默认目标仍为 v1。v2 使用独立 `d012-logical-v2-*` 逻辑身份，v1 原字节不变。

stage 的意图与回执改用现有耐久写接口，原 JSON 字节结构不变。v2 另记录 `datasetSchemaVersion=2`、`rowEncoding=trade_date-v2`；发布 SQLite 仍用原表和互斥锁，新增记录在 JSON 外层写 `protocolVersion=2` 和布局编码。旧日志不补字段，旧解析器拒绝新版包装，新解析器拒绝无版本旧日志。空表的行摘要相同也不能跨版认领。恢复还要再次核对原冻结定义、原目标、原 stage/backup 身份、全部键值和来源原件。

原始 `namechange` 及日级来源证据继续保留原 `timestamp` 编码；v2 的写入和快照使用独立 `trade_date` 行摘要，不给旧来源或旧日志换标签。append 的 v2 意图另标 `java.stk_st_daily_append.v2`，未决仍须显式核对，不能自动重发或解锁。本批未新增 append 未决恢复器，不能拿发布恢复入口替代它。

实库故障演练还发现一个旧缺陷：发布已标 `IN_DOUBT`，适配器却未通过 `recoveryRequired` 告知通用 runner，空会话时 runner 可能按失败释放区间锁。现已补齐回调；已存在发布日志、append 或 stage 耐久意图时都保留原占用。这个修复同时适用于 v1/v2。首次隔离验收的原发布互斥锁仍在，按原协议完成原日志、原 stage 与来源核对后补第二次 rename，没有重建区间锁或重发数据；失败和恢复原件均保留。

后续完整演练用真实 SSE 闭市日历和专属两行夹具，验证撤销闭市日旧行、保留窗口外行、第一次 rename 确认丢失时保留两种锁，再从原账本恢复。它不请求真实 `namechange`，不证明全历史来源或正式迁移。见[发布验证](../operations/cn-time-migration/ST日频v2发布验证.json)。

当前仅开放显式装配。新计划配置、当前注册、公开读取绑定、连续检查点及组入口仍待接通；正式表、MV、旧 stage/backup 和生产默认值未切换。恢复原请求与生成新计划是两条路径，不能用当前配置替换原版本。


## ST 控制服务与同版检查点

`StockStDailyJobService` 由目标作用域声明当前布局，新计划和新运行必须匹配该版。`restorePlan`、`resume` 和已完成来源再验证从原账本读取作业版本，恢复固定 canonical 定义、原 JSON 指纹与逻辑/物理身份，再选择独立同版目标。配置改变不能重绑旧请求；物理表换代和未决状态仍阻断，不重建原锁或重发数据。

连续检查点按原作业版本筛选，同一 targetId 也不能借另一版的已验证前缀。原来源回执保持旧编码，来源原件内容与物理布局版本分别核验，既有逐日全键值回读和开市日历要求不变。

离线验证覆盖两个当前布局方向的原版本恢复、原 JSON 不变、错版新计划、物理换代、未决拒绝、再验证作用域及检查点隔离，见[控制服务验证](../operations/cn-time-migration/ST日频v2控制服务验证.json)。没有执行真实来源、远端写入或真实账本恢复。该批未接配置、当前 Dataset 与组入口，后续范围见下节；公开默认仍 v1。


## ST 配置、读取与 prepared 写入组

根市场配置 `app.sync.stk-st-daily-schema-version: 1` 只接受 `1/2`，标准环境覆盖为 `APP_SYNC_STK_ST_DAILY_SCHEMA_VERSION`。数据应用当前任务、单表计划、目标作用域、类型化仓库和公共读取绑定共用该值。默认仍 v1；配置不建表、不迁数据，v2 遇到旧物理布局先拒绝。

仓库显式保留 v1/v2 契约供原组解析，当前查询仍只使用当前配置版本。prepared 写入组按成员原 `definitionVersion` 选 mapper、行编码和实际 writer，会话错版时在预检及发送前停止。v1 继续走旧工厂和原 `timestamp` 字节，v2 使用独立 `trade_date` 字节。当前默认改变不能给旧组重新标版。

prepared 组只验证并追加预先给定的正记录，不代替来源整窗撤销协议。名称区间修订仍由单表来源流程核验完整证据、stage、backup、窗口外行和发布锁。组仍检查全局未决发布，不自动重发或解锁。

装配、根配置导入与环境覆盖、两个方向的冻结组以及错版会话均做离线验证，见[入口验证](../operations/cn-time-migration/ST日频v2配置与组入口验证.json)。没有新增来源、切换默认、迁移正式表或执行真实组写入；Batch 独立来源、其余两张交易日表、MV、正式调度和完整模型材料仍待验收。


## 停牌存储分版

`stk_suspend` 的逻辑键原本已经是 `trade_date`；v2 只把物理 `timestamp` 换成 `trade_date`。保留 TIMESTAMP 微秒、UTC 午夜日期载体、DAY/WAL、证券加日期完整键、LONG 1 正记录及原来源规则。`suspend_d` 的 S 记录不能扩写成全天停牌。

契约、完整键回读、writer 预检、类型化仓库与稳定快照显式选择布局，不按当前列名猜版本。`forTarget` 创建的独立 stage 会话继承原布局，隔离和 stage 的原准入范围不扩大。

逻辑行字段和含义未改，因此 v1/v2 共用原行编码与快照摘要；不为物理列改名虚构新的行值。相同行摘要不能证明物理布局相同，旧来源请求和旧 prepared 组遇到 v2 会话先拒绝。该批只验证存储；后续 staging、发布恢复见下节，当前 owner、根配置和组 v2 入口仍待接通。

实库测试只读原核查日期的两行，在专属 `java_d011_stk_suspend_layout2_*` 表写两轮，每轮核对完整值、类型化读取、WAL 和稳定身份，再独立按原逻辑 JSON 与长度前缀计算摘要。客户端停止后再次核验全值与身份，耐久保存清理意图后才删本测试的表。失败或未决保留原表与原件，不重发或自动清理。代码及实库范围见[停牌存储验证](../operations/cn-time-migration/停牌v2存储验证.json)。不证明来源全历史、正式调度或正式迁移完成。


停牌首次实库验收第一轮已通过，第二轮后遇到 JDBC `UncategorizedSQLException`（SQLState `00000`）；原测试失败，表和原件保留。原进程终止后，没有重发，另用 HTTP 及 Java 类型化读取、全值快照、独立摘要、原身份和 WAL 核验已落库结果，再耐久记录清理意图，只删除该原测试表。首次失败不计为完整测试通过，JDBC 根因尚未确认；后续独立演练增加每轮发送、确认和回读的阶段记录，不以重跑替代原未决核对。


## 停牌显式 staging、发布与恢复

停牌目标工厂、范围、私有 stage、发布表和稳定快照现可固定同一物理布局。v2 的 CTAS 窗口、指定列、去重键和 INSERT 共用 `trade_date`，保留原 DAY/WAL、微秒日期载体、正记录与窗口外行；不探测现有列或自动补列。v1 原逻辑身份字节保持不动，v2 使用独立 `stk_suspend-logical-v2` 摘要域。身份字符串中的 `static-v2-` 是原身份算法前缀，不是数据 schema 版本。

逻辑行编码仍是 `trade_date-v1`。v2 stage 意图、核验回执和发布 scope 另带精确整数 `protocolVersion=2`、`datasetSchemaVersion=2`，发布日志还冻结 stage 原件 SHA-256。空摘要或相同值不能借用另一布局的日志；字符串版本、浮点版本、溢出计数和浮点强转后的 LONG 行值均不能冒充正确凭证。旧 JSON 不补字段，来源原文和原请求不重写。stage 意图及回执改用现有耐久写接口。

v2 发布在写日志前核对原冻结 canonical 定义、逻辑与物理身份、窗口、stage 原件及完整快照。恢复从原账本选择独立同版作用域，先核验全部原始日级来源、stage、原表或备份及窗口外行，再补缺失的 rename。公开低层 `publisher.finish` 不能绕过新版来源核验；使用 `StockSuspendRunRecovery.finishInterrupted` 或按原账本分发的静态 `StockSuspendPublication.finish`。同版已验证运行可再次核对，不重发数据或重复 rename。该批只接发布恢复；普通来源、控制和检查点的后续范围见下节。该批未接当前 owner、根配置和组入口，后续接通范围见“停牌配置读取与 prepared 写入组”。

故障测试发现 `/var` 与 `/private/var` 的路径别名会让再次核对把同一完成文件误判为另一凭证。现继续用真实路径核验越界，但返回原冻结路径，不给旧引用换字符串。此修复也适用 v1；不是跳过路径校验或改绑文件。

停牌适配器另补 `recoveryRequired`：只读查询原运行的发布归属；append 或私有 stage 已有意图也保留原区间锁。发布已经 VERIFIED、通用完成确认却失败时同样不能释放。普通预检失败不会创建发布表，不访问物理目标。未新增 append 或尚未进入发布日志的 stage 恢复器，不能据此自动重发、清理或解锁。

离线验证覆盖 16 种新旧布局、空窗/非空窗及两次 rename 前后的故障，原 JSON、缺失步骤补做和重复核对；还验证真实 staging 生成器的有界 SQL、微秒绑定、同版工厂和错版凭证拒收。使用临时 SQLite、原件夹具、内存物理表及模拟 JDBC，没有访问外部来源或执行真实 QuestDB 发布。范围见[停牌发布验证](../operations/cn-time-migration/停牌v2发布验证.json)。上一批实库仅验证存储端口，不能替代此发布流程的实库验收；正式表、MV、旧 stage/backup、生产默认和任务 07 均未完成迁移。


## 停牌来源执行与原版本控制

停牌来源执行器、计划、运行、原请求恢复、连续检查点及已完成来源再验证已支持显式同版依赖装配。新请求必须匹配当前目标作用域；恢复与再验证从原账本读取 canonical 作业版本，选独立同版目标，不按当前选择重规划范围或换写请求。该批只接显式执行依赖；Spring 和配置入口的后续范围见下节。

v2 来源仍使用原 `suspend_d` 请求、原始回执、五日预算及原正记录规则。逻辑行编码继续为 v1；append 意图使用独立 v2 标签，完成凭证另绑定布局。目标、主会话和 stage 会话都须匹配冻结版本。正式表仍只允许显式有界 BACKFILL，不借分版开放增量接管。

原追加路径缺少检查点所需的窗口证明，可能导致运行成功却无法续接。新完成凭证现在记录同物理身份的追加窗口证明，与每个页面关联；空页也必须在全表回读前后确认 WAL，未就绪时保留原意图和区间锁。检查点只合并同版完整回执，不能借另一版的连续前缀或缺少 WAL 证明的旧记录。旧 JSON 不补字段、不自动升级；同一旧目标若已有缺证的已完成增量记录，会继续阻断，需要另行明确处置或重新认证流程，不能据此宣称已接管。

再验证固定已核验的物理代际，控制服务检查与适配器构造之间若换表也拒绝继续。完成运行只有原请求物理对象，或其自己的 VERIFIED 发布代际，才可继续核对；行值相同不等于可以重绑新表。整个过程不写目标或推进原检查点。

普通执行链还发现一个重复核对缺陷：已有完成凭证引用原 stage，恢复却给页面换成新快照标签，导致页面和完成证明不一致。现沿用已核验完成凭证里的原 publication；链接已经一致时不重写页面。新旧版适用，原请求、来源、页面和完成原件不会因重复核对而改值。

临时 SQLite 与内存物理表运行了真实来源解析、通用 runner、追加/替换发布、检查点和只读再验证，覆盖两个布局和空/非空来源、相同逻辑身份下版本隔离、两个方向的恢复、原 JSON 不变、WAL 未决保锁及物理换代拒绝。外部请求由有界夹具替代，没有真实来源或 QuestDB 写入；见[控制执行验证](../operations/cn-time-migration/停牌v2来源与控制验证.json)。真实 staging/发布验收、append 及未发布 stage 的恢复器、L2、Batch 和正式迁移仍待完成。


## 停牌配置读取与 prepared 写入组

`app.sync.stk-suspend-schema-version` 位于根 `config/markets/cn.yml`，默认 `1`，只接受 `1/2`；环境覆盖为 `APP_SYNC_STK_SUSPEND_SCHEMA_VERSION`。当前作业、同步目标、读取契约与公共绑定同版；恢复继续按原账本，prepared 组按原成员版本选择会话。停牌逻辑行编码本来就是 `trade_date-v1`，本批不换编码。

读写表名保持原默认：`app.sync.stk-suspend-table` 是 `stk_suspend_d011_isolated`，`app.read.stk-suspend-table` 是 `stk_suspend`。分别通过 `APP_SYNC_STK_SUSPEND_TABLE`、`APP_READ_STK_SUSPEND_TABLE` 覆盖。隔离验收 v2 时须显式指定同版读取表；改布局配置不会迁表、重建正式表或让公共读取跟随隔离写入目标。

组写入仍只追加冻结的正记录，不代替来源窗口替换或撤销。错版会话在预检与发送前拒绝，原全局未决发布保护保留。根配置导入、环境覆盖、两个方向的冻结组和 Spring 无 I/O 装配均有离线验证，见[入口报告](../operations/cn-time-migration/停牌v2配置与组入口验证.json)。没有真实来源请求、QuestDB 写入、正式切换或旧证据重写；真实发布、旧缺证记录处置、append 和未发布 stage 恢复器仍待验收。


## L2 日特征显式存储分版

`l2_daily_features` 的来源 Parquet 继续使用 `ts`；v2 显式契约、mapper、读取和 writer 使用 `trade_date`。原 110 列、DAY/WAL、TIMESTAMP 微秒、完整 `(日期,symbol)` 键及所有指标/null 保留。交易日仍是 UTC 午夜日期载体，不转换成上海事件时刻。v2 读取遇到非午夜载体会拒绝，不截断时分秒。

v1 原契约、默认构造与 canonical JSON 字节保持不变。v2 行摘要使用独立 `trade_date` 键；不能因行值相同就借用旧 `ts` 摘要或修改旧凭证。显式新 writer 仅允许原 D086 隔离命名，正式 factory 仍固定旧表和 v1，不自动建正式表、猜列或迁移历史。

该批只接显式存储端口，没有给当前来源、正式摄取、目标工厂、控制服务、公共注册或配置切换 v2。旧来源按冻结契约检查会话，正式摄取拒绝新版会话，避免存储能力先接通后被旧协议误用。恢复、检查点及原身份保持原样，后续须完整贯通再做真实验收。验证材料见[L2 存储报告](../operations/cn-time-migration/L2日特征v2存储验证.json)；离线测试不能替代真实来源、实库回读、正式迁移或 MV/消费者切换。


## L2 显式目标与来源分版

L2 日特征目标新增按冻结版本取独立作用域的端口。v1 原物理身份字符串与 SHA-256 输入保持不变；v2 在原身份信息前加入独立 `l2-daily-features-layout-v2:` 摘要域，两个版本不能互借检查点。新身份只接正整数表 ID 和非空目录；作用域必须保持原表名与所需版本，不根据当前列名猜测。两版都只允许原 D086 隔离目标，新建与新会话使用同版布局。

来源适配器可显式使用 canonical 作业定义 v1/数据契约 v1 或作业 v2/契约 v2；原预算、依赖的 manifest v1、Parquet parser 和来源原文保持不变。新版会话使用自己的 `trade_date` 行编码，无版本标记的会话只属于 v1。新版请求另冻结 canonical JSON `source_inspection`，包括来源/schema 摘要、parser、日期、行数及完整性；预检先匹配这个原件，再检查当前来源，不能仅凭相同来源根重新认领变化后的文件。旧请求不补字段。预检核对原定义、原窗口、来源根和完整 inspection，不能拿旧定义配新版 writer。

该批只接显式目标和来源。当前控制服务、Spring 配置与公开任务仍为 v1，计划阶段拒绝新版目标，避免尚未贯通恢复和检查点就开放入口。没有新增恢复操作、改写旧请求或把 runner 成功当作正式接管。离线验证使用真实通用 runner 与临时 SQLite，外部来源、物理表和 writer 由端口替代；范围见[L2 来源报告](../operations/cn-time-migration/L2日特征v2目标与来源验证.json)。真实来源、实库、控制恢复和正式迁移仍待验收。


## L2 原版本控制与连续检查点

L2 控制服务按当前显式目标选择新作业，恢复按原账本定义取独立同版作用域。`restorePlan` 不读当前日历、目标范围或检查点；v2 沿用原 `source_inspection`，v1 只恢复原来冻结的范围与来源根，另用原 FETCHED 页面指纹核对当前文件。没有给旧请求补 inspection、改任务身份或重发未决记录。

会话在构造、预检、发送、回读、范围计数和 WAL 检查前后核对原物理身份，并核对 writer 表名与布局。配置切换或同名换表不能重绑旧运行；发送后物理变化按原通用执行器保留未决。只读再验证的会话拒绝发送。执行前的原页面预读计入同一原超时预算；恢复计划里的原范围检查仍是独立的有界只读操作。

v2 执行、显式 RECONCILE 和已完成来源再验证增加最终完整范围核对：重读同一来源，逐业务键比较全部字段，再按日期及同一证券筛选范围计数，排除缺键和多余键。闭市日也须为零；其他证券的数据不删、不算进此筛选范围。回读及计数前后固定同一已应用 WAL 事务版本。数量、ACK、原成功状态均不能单独证明完成。`java.l2_daily_features_scope.v2` 是复核协议，实际存储布局另由 `layout` 记录。

增量从显式起点拼接连续、独立复核通过的自然日窗口，不直接取 `MAX(to)`；未覆盖的休市区间也不按星期猜补，可用包含该区间的有界作业补齐证据。优先选择覆盖更远的范围，同终点按验收时刻选新证明。旧来源修订导致原范围无法再次核对时，可采用另一条当前独立通过的证明；本次未采用的原运行和成功回执分别写入检查点核验报告，旧账本不改。已验证父项却含未决或缺证子项时继续阻断，不能靠另一条成功记录掩盖。

显式 BACKFILL/RECONCILE 只用旧 canonical 请求及页面证明确认目标归属，不把旧值当作当前已完整；有界修订必须重新验收。这样可修复旧来源修订，且不放行无归属的物理数据。非增量计划的 `verifiedThrough` 保持 null。原目标日期扫描改为最多读取 33 行，检测超过原 32 日上限，不再截断后当作全目标范围；此修复也适用 v1。

CLI 的 `run-l2-daily-features-job --resume-from <原runId>` 直接恢复原请求。额外提供的日期、模式或证券只用于核对，必须与原请求一致；不再调用当前 `plan`。示例，先把 `RUN_ID` 换成原账本里的运行 ID：

```sh
./gradlew :markets:cn:data-app:run --args='run-l2-daily-features-job --resume-from RUN_ID'
```

断点可从 `L2Commands`、`restorePlan`、`verifyOriginalPages`、`L2DailyFeaturesBoundSession` 依次进入 `SyncJobRunner.resume`；检查点看 `verifiedWindows`、`continuousThrough` 和 `revalidate`。执行预算、业务日期及 Parquet 来源名不改；配置入口、正式摄取、真实实库和正式迁移尚未切换。离线验证范围见[控制恢复报告](../operations/cn-time-migration/L2日特征v2控制恢复与检查点验证.json)。


## L2 配置与散户情绪 MV 同版

`app.sync.l2-daily-features-schema-version` 默认 1，只支持 1/2。当前 L2 目标、作业、读取和组 mapper 同版；散户情绪 MV 的任务依赖、来源、SQL、读取契约一起选版，不能只改任务图的依赖版本。

v2 L2 来源须显式使用 `java_d086_l2_daily_features_` 加非空后缀；MV 目标须使用 `java_d098_mv_retail_sentiment_daily_` 加非空后缀。MV 默认隔离目标在根配置维护。原正式摄取继续写 v1 的 `l2_daily_features`，配置不触发正式迁移。

散户情绪输出原本就是 `trade_date`。v2 仅调整来源日期列与 lineage，保留 13 列、原 AVG/SUM、金额单位、null、MONTH/WAL 和原生定时刷新。v1 定义、身份摘要与行编码不重写；v2 物理身份使用独立摘要域。公共读取检查明确来源和完整 SQL，旧游标不能跨作用域复用。

CREATE 自身会聚合数据。v2 创建前须证明整个隔离来源不超过 31 个自然日和 200000 行，并核对精确计数、完整键及稳定 WAL；空来源须有零计数和空边界。空表安装不等于来源覆盖验收。FULL 仍须通过原私有实例准入，冻结请求不能绕过当前写入开关或部署身份限制。

历史恢复和 status 从原账本选版、选表，原来源变化时拒绝恢复；不改原 JSON。未知发送保留原锁，显式确认发送方已停后才允许只读 reconcile，不能自动重发或解锁。

MV 连续检查点按原成功窗口与子项证明确定范围，再用当前来源创建独立只读复核请求，核验完整值、计数、日历和前后稳定快照。新证据关联原运行并记录 `verifiedAt`，不把当前来源版本写回历史请求，也不把核验时刻当成历史可用时刻。MV 无效或尚未追平时拒绝推进，需等定时刷新或明确有界 materialize 后重试。

本批配置、SQL、恢复和检查点仅做离线验证。真实 L2 文件、真实 MV 创建/刷新、正式表与消费者切换仍须单独验收，见[验证记录](../operations/cn-time-migration/L2日特征与散户情绪v2配置链路验证.json)。

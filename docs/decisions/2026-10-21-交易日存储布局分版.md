# 交易日存储布局分版

先保留旧布局，再显式接入新布局。`etf_adj` 的旧端口把 `timestamp` 写死在预检、范围、完整键回读和日期盘点中；只改 DDL 会让原任务读写失败。反过来按实库“碰到哪列就用哪列”，又会让冻结请求的版本失去意义。

`CnTradeDateLayout` 只允许已核定的六个对象。v1 保留原来的 `timestamp/ts`，v2 选择 `trade_date`；利率、公告、技术 epoch 和待核对象不能套用。它只选择布局，不转换日期、不加八小时，也不改变类型精度。存储布局 v2 与主策略输入协议 v2 是两件事。

本批只接通 `etf_adj`：

- 契约、隔离 DDL、范围查询、写前预检、完整键/整日回读和类型化读取共用显式布局。
- v2 仍使用 TIMESTAMP 微秒、UTC 午夜日期载体、YEAR/WAL 和原完整业务键；来源 `trade_date`、原始日期及复权因子数值不变。
- 原 `EtfAdjWriteSession` 代表固定 v1；分版会话显式实现 `Versioned`。适配器核对冻结定义与会话版本，版本不符时在日历、来源和物理预检前停止。
- `EtfAdjSyncJobOwner.definition(2)` 生成独立 v2 定义和请求身份。原 `DEFINITION`、兼容构造及公开默认值仍是 v1，不改写已有请求、回执或检查点。

控制服务已接通显式 v2 装配：新计划和新执行使用选定布局；恢复、已完成来源再验证及原日志核对使用原账本的作业版本。配置和组入口的范围见下文；其余五张表端口、Batch 独立来源任务、正式表、MV 和消费者没有迁移。

## 怎么核验

离线回归核对版本不符先失败、原 v1 默认与编码不变、新布局列名、完整键回读、日期精度、WAL 和目标身份检查。新布局遇到旧物理列或新物理身份时，不能借 Sender 自动补列或继续发送。

实库验收使用已有正式表的两行只读样本，先耐久保存期望、DDL 意图、目标身份和 v2 请求，再写唯一的 `java_d015_etf_adj_layout2_*` 表。每次发送后核对完整键值、类型化读取、行数、WAL 与稳定身份；第一次全部通过后才做第二次幂等写入。客户端停止后，只清理本测试创建且身份未变的表。

```sh
APP_LOCAL_CONFIG=file:/绝对路径/config/application-local.yml \
D015_LAYOUT_LIVE_ACCEPTANCE=true \
D015_LAYOUT_EVIDENCE_ROOT=var/etf-adj-layout-acceptance \
./gradlew :markets:cn:data:test --tests '*EtfAdjLayoutLiveAcceptanceTest'
```

默认不运行此实库测试。证据目录存在未完成记录时先停止；写入未决不自动重发或删表。报告只写错误类型，不复制账号和异常中的配置。未尝试 DDL 的失败可以重新运行；已尝试建表的失败需先人工核对原表和原件。

实际两行验收已通过，隔离表已清理，正式表身份与事务版本在验收期间不变。它验证 Java 读写布局，不证明来源完整、全历史、模型批准或正式迁移已完成。结果见[实库原件](../operations/cn-time-migration/ETF复权v2端口实库验收.json)和[代码验证](../operations/cn-time-migration/ETF复权v2端口代码验证.json)。

## 控制服务怎样保留原版本

`EtfAdjJobService` 的显式构造参数只用于新计划。原有 `--resume-from` 分支直接恢复账本，不重新规划今天的范围或检查点；通过账本 `jobVersion` 选择固定的 canonical 定义，再校验原 JSON、请求指纹和目标身份。当前默认换成另一版也不改写原请求。新运行则必须匹配当前显式选择，不能拿旧计划冒充新版新运行。

目标的 `Versioned` 能力按请求版本创建会话和读取范围。旧目标接口仍固定 v1；返回会话的声明版本也要再核对，不能由旧包装器偷偷返回 v2 会话。原物理身份变了就停止，不能因为逻辑表名相同而改绑。

检查点只合并同一版本、同一目标的原完整回执。即使人为使用相同目标身份，v2 也不能拿 v1 回执拼接连续前缀。原 `IN_DOUBT` 状态仍禁止直接恢复；原日志核对仍先确认写入进程停止，并要求原区间锁、原来源和原写后证明，未满足时不写数据、不释放锁。

这些变化用临时 SQLite 和原冻结 JSON 验证，包括两种配置方向的旧版本恢复、缺失原锁及连续区间跨版本混用。没有执行真实恢复、变更生产配置或清理未决记录，范围见[控制服务验证](../operations/cn-time-migration/ETF复权v2控制服务验证.json)。

## 配置与组入口

根 `config/markets/cn.yml` 的 `app.sync.etf-adj-schema-version` 默认 `1`，只接受 `1/2`；标准环境覆盖为 `APP_SYNC_ETF_ADJ_SCHEMA_VERSION`。同一个值装配新作业注册、单表计划服务、目标端口、读取仓库和公共读取绑定。新配置不建表、不迁数据；v2 碰到旧物理列时仍须在发送前拒绝。

`DatasetImplementation.definition(version)` 默认只接受当前版本。只有显式实现的 owner 才能提供历史契约；注册表再次核对数据集、版本、provider、owner、对象名和对象种类。`etf_adj` 显式保留 v1/v2，其他实现没有因此自动开放历史版本。

写入组从 JSON 解析、计划指纹、作业注册到实际 writer 都按成员 `definitionVersion` 选择。旧组在当前配置为 v2 时仍使用原 v1 契约和原指纹；反向也一样。实际会话错版时在预检和发送前停止。原目标身份、完整键值、WAL、区间锁和未决恢复规则不变。

该设置控制数据应用的当前 `data.etf_adj` 注册，不改写 Batch 独立 `source_etf_adj` 任务、已有 Quartz 元数据或冻结组请求；正式调度和迁移须另按原部署验收。其他五个物理日期别名也未因此切换。验证见[入口验证](../operations/cn-time-migration/ETF复权v2配置与组入口验证.json)。

## ETF 日线接入范围

`etf_daily` 的 v2 契约、隔离 DDL、范围、完整键/整日回读和类型化仓库均显式选择 `trade_date`。保留 `TIMESTAMP_NS`、UTC 午夜纳秒载体、YEAR/WAL、去重键含义及原十一列数值和空值；不套用复权表的微秒处理，不自动探测列名或自动补列。

根市场配置新增 `app.sync.etf-daily-schema-version: 1`，环境覆盖为 `APP_SYNC_ETF_DAILY_SCHEMA_VERSION`，只接受 `1/2`。单表新计划、当前作业、目标和公共读取绑定共用它。默认仍 v1；`EtfDailySyncJobOwner.DEFINITION` 及旧构造保留原定义。

恢复、已完成来源再验证、原日志核对和检查点都按原账本版本。恢复核对原 JSON 指纹和目标；新计划不接受与当前配置不同的版本。新会话通过 `EtfDailyWriteSession.Versioned` 声明布局，旧泛型会话仍固定 v1；写入组也核对实际会话。日线原有的来源预算、正式表仅允许有界 BACKFILL/RECONCILE、停机日志、区间锁和不确定写入处理保持不变。

实库验收与离线验证分别记录在[日线验证报告](../operations/cn-time-migration/ETF日线v2验证.json)。它们不证明来源全历史完整、正式调度或模型批准。Batch 独立 `source_etf_daily`、其余四张物理别名、MV 与消费者正式迁移仍待完成。

## ETF 份额接入范围

`etf_share` 原作业是 v3、数据契约是 v1。新布局使用作业 v4、契约 v2；`definition(jobVersion)` 只认已登记的 v3/v4，`forLayout(schemaVersion)` 才按布局选作业。不能把旧作业重新编号为 v1，也不重建未登记的更早作业协议。

根市场配置新增 `app.sync.etf-share-schema-version: 1`，环境覆盖为 `APP_SYNC_ETF_SHARE_SCHEMA_VERSION`，仅支持 `1/2`。当前 owner、计划、目标、类型化仓库和公共读取绑定共用它。写入组的成员版本仍是契约 v1/v2，不是作业 v3/v4。

只把指定日期列从 `timestamp` 换为 `trade_date`，保留 TIMESTAMP 微秒、UTC 午夜日期载体、YEAR/WAL、六列值和原完整业务键。`update_time` 仍为独立 UTC 观察时刻；新来源计划冻结一次 `observedAt`，恢复继续用原值。旧物理样本每行已有不同 `update_time` 时，迁移逐行保留，不能覆盖成统一的新时刻。

检查点按原作业版本筛选全部回执，包括修订值的最新凭证；v3/v4 不能拼接连续前缀或借用修订值凭证。普通恢复仍核对原 JSON 指纹和物理身份，未决状态不允许自动重发或解锁。既有 366 日、SH/SZ/O 三市场分片、5997 行日期上限、预算及来源原文核验均保留。

生产仓库、目标和 writer 继续只接受 D016 隔离命名空间，没有借分版开放正式表。实库演练只读正式表两行，按显式 prepared 写入组冻结各行原值，再验证独立 v2 表；它不冒充按统一观察时刻生成的新来源同步作业。范围见[份额验证](../operations/cn-time-migration/ETF份额v2验证.json)。Batch 独立来源、正式接管、调度、其余三表、MV 与消费者迁移仍待完成。

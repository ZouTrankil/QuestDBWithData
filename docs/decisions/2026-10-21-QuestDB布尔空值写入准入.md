# QuestDB 布尔空值写入准入

## 要解决什么问题

原生 MV 的实库夹具暴露了存储限制：L2 的 `has_deal/has_order/has_snapshot` 传入 `null`，QuestDB 回读为 `false`。原可空 DTO 和模拟 JDBC 都不能证明物理表支持三态布尔；完整值核验因此失败，不能把它当成可见性延迟后继续重发。

QuestDB 的 [BOOLEAN 类型不可空](https://questdb.com/docs/query/datatypes/overview/)。manifest 的 `daily_feature_ok/t0_ok` 也使用 BOOLEAN，遇到同样限制。`false`、未知和缺少整行不能互相冒充。

## 本次怎么处理

保留原来源 DTO、NULL 编码、任务版本、冻结 JSON 和物理列。来源解析与历史编码仍可表达未知，但不能把不可表示的值发送到 BOOLEAN 列，也不把未知补成 `false`。

公共 `DatasetWritePreparation` 拒绝可空声明中的 BOOLEAN `null`。`VerifiedBatchExecutor.Codec.validateForWrite` 在提交意图之前执行，默认不增加规则；L2 日特征与 manifest 显式接入。直接日特征 writer 在借 Sender 前执行同一校验。正式摄取先检查全部缺口的可写性，再开始第一批发送，避免较后非法行导致前批已写。

其他可表示的数值、计数和文本 NULL 不改，明确给出的 `false` 可以写入。旧定义的 `nullable` 只保留来源模型含义，不能据此推断 BOOLEAN 的物理能力。需要持久保存三态布尔时，须另做明确的版本化存储设计；本次不改列类型或重标旧 schema。

## 原失败怎么处理

首轮只写了本任务的私有来源和日历，尚未创建 MV 或运行账本。发送进程终止后，按原目标身份、稳定 WAL 和完整字段逐项核对，证明差异仅为原始 NULL BOOLEAN 变成 `false`。先保存作废清理证据，再删除本次原身份对象；原输入与失败报告不改，不计作验收成功，也没有重发。

后续夹具明确给出已知布尔状态，仍保留其他字段 NULL，并使用独立手写聚合期望。它是新的有限测试输入，不是修补原失败输入或伪造正式来源。

## 验证与剩余限制

准入回归覆盖三个日特征标记、两个质量标记、两个日期布局、公共准备和执行器，以及正式摄取的后续非法行场景。成功发送与恢复夹具改为明确可写布尔值；原 NULL 编码、来源解析和保留 golden 不改。

历史表中的 `false` 无法单独证明当初是真实 false，还是由未知值写成。须用原来源逐键核验，不能仅凭当前行数、布尔值或新代码通过就宣布旧数据正确。真实 Parquet 原件、正式迁移与完整模型验收仍待完成。范围及原件见[实库记录](../operations/cn-time-migration/L2布尔空值准入与原生MV实库验收.json)。

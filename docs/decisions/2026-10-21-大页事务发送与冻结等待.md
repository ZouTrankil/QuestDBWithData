# 大页事务发送与冻结等待

新大页请求使用 v4，把 QWP 事务分帧和 600 秒可见性等待同时冻结。旧 v1/v2/v3 的发送方式和五分钟等待保持。旧未决运行先核对原证据，不能换新版本重发。

## 已发生的问题与恢复

v29 的逻辑大页仍按普通客户端方式提交每个传输帧。2010 年 10465 行已完整验收，但原组 `broad-b5d4d0c1-2ede-44c1-8d80-809b2e724da9` 的第 10 窗口，即 2016 年的 19965 行，在全部发送确认后超过五分钟核验上限。原 PID 41396 退出，运行 `market-8711c15e-684d-4497-b0a3-fe1dd5772dc7` 保留 `IN_DOUBT` 和原锁。

原进程停止后，从 128 份原 Yahoo 响应独立重建二十列，与 prepared、HTTP 和 PGWire 全部一致，WAL 为 3619/3619、无缓冲及挂起。使用原 prepared 摘要执行 `reconcile-complete-frozen`，再用 `reconcile-broad-window` 推进原第 10 窗口。补写价格为零，最初失败回执、此前十个已验收窗口和剩余未发送窗口均保持。07:21 UTC 的独立复核确认原窗口与原生账本均为 `VERIFIED`，没有未决原生记录。

证据在 `var/market-data/scope-review/bulk-pages-20261021/2016-original-recovery/`，包括恢复前全量核对、原进程停止证明、两个 Java 恢复日志和 `readonly-recovery-independent-verification.json`。

## 发送与冻结约定

- 新大页仍最多 32768 行、32 MiB；年度 ZIP 清单仍为 v2，原来源和窗口不重建。
- 新原生请求 v4 必须声明整数 `publication_visibility_seconds=600` 和布尔 `publication_transactional=true`，prepared 的 `publicationPolicy` 保存相同整数和布尔值。缺失、字符串替代、非整数、策略不一致或降级均拒绝。
- 客户端使用 `transactional(true)`，自动分帧容量继续为一万行和四 MiB，并接受服务器协商的更小字节上限。整批显式刷新后等待全部发送确认；恰好整万行且最后没有数据帧时，也必须完成最终提交确认。
- 单批可见性上限十分钟，新 v4 单运行上限一小时，来源总量仍最多十万行。共享执行器只提高可声明上限；实际等待取适配器策略，并按原任务剩余时限裁剪。
- 旧 v1/v2/v3 不能添加新发送参数或 prepared 策略，恢复继续使用普通分帧及五分钟等待。旧 v2 容量仍不超过 10000 行、8 MiB，旧 v3 大页仍可按原声明解码。
- 显式未发送尾部续接同样从原请求恢复事务模式和等待。全部来源键值、原物理对象、WAL、取消、发送前意图及不确定结果不重发的规则继续执行。
- 少量缺键的明确授权修复同样使用原事务模式；旧修复的两分钟 WAL 等待保持，v4 使用原冻结的 600 秒。

[QuestDB QWP 协议](https://questdb.com/docs/connect/wire-protocols/qwp-ingress-websocket/)说明延迟提交可把多帧组成一个逻辑批次；中间帧确认不能代表最终提交。这里采用当前 Java 客户端的事务模式，不手工切换实现类的延迟提交标志。

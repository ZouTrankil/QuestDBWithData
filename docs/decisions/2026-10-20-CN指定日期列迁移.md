# CN 指定日期列迁移使用新物理对象

当前目标 QuestDB 实例拒绝直接改名指定时间列。六项交易日别名不能用一条 `RENAME COLUMN` 完成；正式迁移采用新布局对象、完整键值核验和协调切换，不能原地假设成功。

已用 Java 有限维护入口在六组专属隔离对象上演练新表方案，每组最多两行。复用 `SHOW CREATE` 的定义，明确映射列声明、指定时间列和去重键，其余类型、分区及布局不变。`etf_daily` 保留 `TIMESTAMP_NS`。先核验旧副本 WAL，再复制到新布局，等待新副本 WAL 稳定，按存储整数比较时间与全部样本字段，并核对旧副本仍保持原样。新对象 ID 单独记录，不复用旧凭证。

字段类型、指定列、去重键、有效索引和缓存规则必须一致；`symbolCapacity` 随字典增长，未启用索引的块容量不代表业务布局，不能用这两个运行量误判两行副本。清理只允许本轮随机命名且物理 ID 未被替换的隔离对象；其他对象拒绝删除。

六组新表演练均通过，副本全部清理；正式对象身份及指定列复查未变。[实际结果](../operations/cn-time-migration/新布局隔离演练.json)和[复查](../operations/cn-time-migration/演练后复核.json)已保存。前期直接改名失败、系统函数常量参数限制和 WAL 等待失败不算完成，分别保留结果说明。

这只是小样本结构演练，尚未演练正式换名、原生 MV 重建、原账本恢复或全窗口历史比对。正式切换仍需停写证据、旧请求/回执版本归属、完整数据核验、消费者部署及批准模型材料。不能因为样本通过就改变正式别名或清理旧对象。

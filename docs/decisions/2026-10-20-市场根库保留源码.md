# 市场根库保留源码

保留 `:markets:cn`、`:markets:us`、`:markets:btc` 作为 Java 库，同时聚合子项目。不新增 `src`、`model` 或 `contracts` 子模块。本次解决归属不直观的问题，不迁包、不改变模块坐标。

## 核对结果

| 库 | 直接源码与资源 | 直接依赖 | 当前消费者 |
| --- | --- | --- | --- |
| `:markets:cn` | 260 个 Java 文件；模型、契约、DTO、目录及字段资源；目录 SPI | core、Jackson | CN source/data；engine 仅测试依赖 |
| `:markets:us` | 23 个 Java 文件；美国利率及基础行情、来源规则与目录；目录和来源 SPI | engine:source | US data-app；CN data-app/主策略运行时；CN Batch 测试运行时 |
| `:markets:btc` | 5 个 Java 文件；时间、币价定义、映射与目录；目录 SPI | core | BTC data-app |

数量为 2026-10-20 本轮退役后的直接 `src/main/java`，不含子项目。US 根库不是纯模型库，CN 根库也不是纯 JDK 模型库。三个库没有独立启动入口，入口在各自 `data-app`；CN 主策略与实时 L2 另有入口。

## 为什么不拆

抽到一个新叶子模块只会移动同一组源码、资源、SPI 和依赖，不能降低当前任一消费者的传递依赖，也没有新消费者需要更小的契约边界。代价是修改 Gradle 坐标、生成路径、架构基线和发行包，增加一次兼容迁移。当前没有确认边界违规或构建故障，收益不足。

目录中的 `src` 只是 Gradle 标准源码目录。`markets/cn/src` 归 `:markets:cn`，`markets/cn/data/src` 归 `:markets:cn:data`，二者不重复装入同一个 jar。顶层 `platform`、`markets` 仍只聚合，不输出业务 jar。

未来若出现只需要契约、却被迫引入来源客户端或框架的具体消费者，再按真实依赖拆分。沿用现有架构和模块边界检查；不因目录层级相似机械统一市场结构。

## 验证

本轮 `architectureTest`、`verifyModuleBoundaries` 和 CN `distZip` 已通过。此次只补结构说明，没有模块迁移、数据迁移或新增外部作业。

# 未发布隔离 stage 的显式取消与重采

融资融券汇总未发布 stage 的恢复现在分成两步：显式丢弃并取消原运行，再由用户执行 resume，按原冻结请求整窗重抓。不会把丢弃算作采集成功。

## 原因

此前丢弃 stage 后只释放区间锁，原运行仍为 `IN_DOUBT`，公开读取和恢复继续阻断。直接复用旧的 VERIFIED 分片也不成立：它们验证的是已经丢弃的 stage，不能证明新 stage 已有这些数据。

## 处理顺序

1. 用户确认原任务和发送器已停止。持有原发布操作锁，确认没有发布 journal；有 journal 就走原发布恢复，不允许丢弃。
2. 恢复原 v1/v2 冻结定义、日期和目标，保留原租约。核对原表物理代、稳定 WAL、全部行与原基线一致，只删除该运行拥有的隔离 stage。
3. 核实 stage 消失并再次核对原表，保存丢弃意图，绑定原请求、原租约、stage 原件摘要和全部账本项修订。
4. SQLite 单事务将原运行、尝试和分片追加为 `CANCELLED`。明确记录 `dataVerified=false`，保留原请求及全部历史事件；不生成成功或覆盖检查点。
5. 再次核对原表及 stage，保存最终凭证，最后解除原租约。此步失败时，即使账本已经取消，锁也保留，沿相同意图重试。
6. 用户单独执行 resume。新运行保留原父链和完全相同的冻结请求，重新抓取完整范围，不复用旧 stage 的分片。普通恢复及组子任务共用这个规则。

通用账本新增专用 `cancelDiscardedStageRun`，要求原状态 `IN_DOUBT`、耐久凭证、完整清单、对应事件及精确修订。普通 `transition` 仍不允许 `IN_DOUBT -> CANCELLED`。该接口不适用于已经触达正式目标的未决写入，也不替代调用方的真实存储核验和发布锁。

## 限制

原租约、冻结原件或目标归属缺失时不接管。已有 `FAILED`、`PARTIAL`、普通 `CANCELLED` 历史不会借此改成成功。原表改变、stage 重新出现、子项或原件被改动时拒绝重试。正式生产 writer、来源范围队列和周期调度另行验收。

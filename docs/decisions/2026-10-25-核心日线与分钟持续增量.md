## 持续补数怎样执行

新增 `collect-core-incremental --from <日期> --through <日期> --maximum-jobs <上限>`，原 `collect-core` 保留历史回补用途。持续任务固定从 2026-10-22 寻找尚未登记的日期，不拿最新日期代替中间缺口。截止日须已过纽约 20:30 的来源就绪线。

原队列中的所有范围都保留归属，包括失败、已下载和未决任务；不会清状态或换任务 ID 重发。新范围按验证过的纽约交易日历切分，每个窗口最多七个日历日，休市和已覆盖日期不请求。当前日历仅支持 2026 年，夏令时及提前收盘用原日历计算，未知年份停止。

新数据用原 Java writer 的 `publishMissing` 只补缺失键，原物理表、业务键、唯一发布者及恢复协议保持。已存在但不同的值拒收，不自动修订历史调整价。日线必须覆盖窗口内全部开市日期，分钟必须覆盖全部正常时段格点；来源缺失不补零。盘外原文仍保留原表，研究读取正常时段视图。

队列只接受 `VERIFIED`、无错误且来源行数与完整回读行数一致的结果。1 分钟成功后保存原运行，5 分钟也成功才推进整个任务；半途失败保留 `PUBLISHING`，先核对原 Native，不能重新发布。这个检查同时修正旧入口可能把非成功返回推进为成功的问题。

请求沿用原持久预算，默认间隔由根配置 `tiingo-request-spacing-ms: 2000` 控制；单个增量响应上限 2 MiB。Starter 仍按每小时 50 次、每天 1000 次、31 天 500 个标的及 1 GiB 限制执行。旧未知请求及字节预留保持，不通过重启清零。

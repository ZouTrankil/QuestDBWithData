# 回测 MV 固定停牌和 ST 来源布局

原 `mv_backtest_daily` 的 SQL、读取端口和来源键检查都固定使用 `stk_suspend.timestamp`、`stk_st_daily.timestamp`。两张来源可以独立迁移，直接改原 SQL 会改变旧读取的来源；只改物理输出名又可能跳过原生 MV 的读取保护。

## 采用的做法

`BacktestDailyScope` 固定停牌表、ST 表、各自日期布局和输出。原完整作用域继续返回原 v1 定义与原 SQL；其他声明使用读取契约 v2，输出必须在 `java_backtest_v2_` 下。行情、涨跌停仍固定 `stk_factor`、`stk_limit`，依赖登记仍使用逻辑数据集 ID。

新 SQL 只替换两侧来源、对应别名的日期列和输出名。原 ASOF、停牌沿用前收盘、成交量/金额补零、其他 NULL、单位、13 列、MONTH 分区及 `REFRESH IMMEDIATE` 不变。每侧可选布局 1 或 2，不要求同时迁移。

公开读取从完整定义还原原作用域，再核对原生 MV SQL、四个来源的物理身份、WAL、去重键、指定日期列和精度。关联来源在刷新开始后提交时继续拒绝读取；必须保持其他来源先写、`stk_limit` 最后写的原规则。读取前后及分页游标仍绑定同一来源版本。

以数据集 ID、原输出名和专属新版输出前缀识别保护范围。换名、改 schema 号或删改字段映射不能跳过保护；只有完整 canonical 定义可通过。原始业务日期不加时差，旧定义和旧 SQL 不重写。

## 配置与边界

根 `config/markets/cn.yml` 的 `app.materialized-views.backtest` 选择**读取**作用域，默认 v1。`layout-version: 2` 后可分别配置 `suspend-table`、`suspend-layout-version`、`st-table`、`st-layout-version` 和 `v2-output-table`。原 v1 声明不能重绑来源。

这些配置与同步目标分开，避免切换一个 writer 就让原正式消费者读取另一对象。类型化仓库和公开读取注册使用同一声明。配置不建表、不建 MV、不刷新、不接管 writer，也不改变历史请求或来源凭证。

因子计算、情绪和市场状态等直接消费者仍绑定原正式对象；不能据此宣布它们或正式 MV 已迁移。正式切换还需全来源、完整键值、修订刷新、消费者及原恢复归属的协调验收。当前分版测试只证明显式读取和拒绝边界，不代表真实来源或正式数据已验收。

后续实库发现：基表最后提交和水位追平仍不足以证明历史 ASOF 沿用价正确。现在另按原始 SQL 分月核对完整键值，原定义不重写，见[历史沿用价核验](2026-10-21-回测MV历史沿用价完整核验.md)。

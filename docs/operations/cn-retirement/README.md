## 正式环境还缺什么

当前能读取 QuestDB 元数据，但没有定位到实际部署机的正式调度、原同步账本和锁。仓库本地空账本不能证明远端没有未决写入，也没有证据证明本地代码已部署到所有消费者。因此现在不执行 DROP。

1. 在运行该环境的部署目录停掉对应调度和写入进程，部署本轮 Java 与 Python 消费端变更，记录进程与版本。
2. 核对原账本中的三项运行、未决请求、锁及专属 stage/backup；按原恢复协议处理。不要自动重发或强行解锁。
3. 导出三张表结构、必要恢复材料、视图及原生 MV 定义，逐项确认真实依赖。记录需要删除的专属附属对象；不猜前缀、不删除共享账本。
4. 满足条件后，通过 Java 维护链路或数据库维护会话逐句执行[清理 SQL](三项退役清理.sql)。它没有挂到启动或 Flyway，不会自动执行。
5. 保存执行结果并复查不存在、没有重建、消费者没有缺表请求。随后才能将任务 08 标为完成。

[清理前元数据](清理前元数据.json)只证明本次读取时的结构，不证明停写、恢复完成或消费者部署完成。旧审计和已执行迁移保留历史名称。
